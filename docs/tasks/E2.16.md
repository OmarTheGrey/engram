# E2.16 The content guards: three gaps closed and the oracle taught the stage

Status: planned, absorb plan 2.

From `docs/tasks/absorb-plan-2.md`, pull request 13 of 30 (research plans none (cards E2.9's and D1's follow-ups) in `docs/research/absorb/long-list.md`). Lane: research. Week: W11. Effort: M. Read AGENTS.md, the plan's entry for this card and `docs/conventions/absorption.md` before starting.

Goal: The guards scan `provenance.ref`; adoption deny events carry a keyed hash, not a plain sha256; the secret-name rule matches words, not substrings; the oracle knows the content-guard stage.

Why: A credential in a ref is never scanned; a short secret can be confirmed by hashing guesses against the log (ADR 0039, decision 4); `max_tokens` loses its value in bypass reasons; and the invariants say nothing about a policy with guards on, which proposals P1 and P2 need before registration.

1. Failing tests for each gap.
2. The ref scan with its own reason wording.
3. An HMAC with an injected key in `adopt.ts` deny events.
4. A word-based `SECRET_NAME` in `bypass.ts`, shared with the recorder's scrub.
5. The guard stage in `oracle.ts`; guard-on policies in the generated set.
