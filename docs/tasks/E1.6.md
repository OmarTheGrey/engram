# E1.6 The tamper-evident event log

Goal: An edit, a deletion, a reorder or a truncation of the event log is detected by `engram log verify`, and an offboarding's erasure of a person's content still leaves the log verifiable.

Why: Every guarantee Engram gives is read off its log, and the log is append-only by convention only: nothing stops a row being edited in the database. Offboarding makes a plain hash chain impossible, because it rewrites event bodies to erase content. ADR 0038 is the design that keeps both.

Steps:

1. A side table created in `packages/core/src/db/migrate.ts`: per event, a chain hash over the previous hash and the skeleton ADR 0038 defines: the whole event body, with exactly the parts `offboard.ts` rewrites replaced by salted commitments (an item's content, its provenance ref, hash and session entry id; the evidence part of a lint event's reason). Everything else, the reason of every other event included, is hashed as it is. An erasure deletes the salts and the commitments still stand. `schema.ts` does not change.
2. A drift test: redact a generated event exactly as offboarding does and assert the skeleton hash is unchanged; assert any other single-field edit changes it.
3. Each offboarding adds a manifest to the chain: the sorted sequence numbers of every event it redacted, item events and lint events alike.
4. One canonical-JSON function used by the writer and the verifier (UTC timestamps at fixed precision, integral numbers, sorted keys), with RFC 6962's leaf and node prefixes, a genesis per log, and a head-and-count anchor in a meta row against tail truncation.
5. The chain starts after the migrations that rewrote bodies in place, with a backfill checkpoint that says so.
6. Signed checkpoints: the signing function is injected, so core does no key I/O. The CLI supplies an Ed25519 key the operator holds.
7. `engram log verify`: an ordered verifier that reports the first broken link, and UNSIGNED as a verdict of its own when a checkpoint carries no signature. An event whose salts are gone verifies as erased only when its sequence number is in a chained manifest and its redacted parts hold the redaction marker; a missing salt or a blanked part with no manifest entry is reported as tampering.
8. A property test on SQLite and Postgres: random operations including an offboarding, then an injected edit, deletion, reorder and tail truncation, each detected, together with a rewritten reason, an edited item field such as the owner, and a forged redaction (a part blanked and its salt deleted with no manifest entry). An offboarding that redacts a lint event about another item still verifies. It lives in its own file, `chain.test.ts`, which `make test-invariants` runs, and is counted as the next invariant in AGENTS.md (the ninth if card E2.11 has landed, the eighth otherwise). The lead-owned invariants file is not edited.
