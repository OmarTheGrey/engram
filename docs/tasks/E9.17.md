Steps:

1. Settle the dogfood's shape in a `decision` entry, against three constraints: rule 12 (no content leaves a member's machine, so each member keeps their own log); loopback only and self-asserted identity (ADR 0027), so a second member cannot approve on another's machine; and review for promotion (ADR 0026), which needs a user-sourced member of the target who did not write the item. Recommended: each member runs a second `engram serve` under the Knowledge profile on its own port, over a separate folder and a separate log, writing what they learn about the project (decisions, conventions, how-tos) into their person scope and proposing it to `team:engram`; promotions stay candidates the report counts as asked, since no second member is on the machine; the knowledge is about this repository, so it is no more private than the repository, and still only counts leave the machine.
2. Tests first (`packages/core/test/unit/dogfood-knowledge.test.ts`): under the Knowledge profile, a clean fixture log (person writes, a promotion asked into team, an org write from a cited document with its hash) reports zero violations; each seeded violation is found once: a team or org item read before its approval, an org item from a tool or model source, an item read outside its validity window, a promotion approved by its own writer.
3. Fix the report only where a test shows the oracle does not know a Knowledge rule (it was built on the twin's), each fix in core with its own invariant-file test; if a rule is beyond the oracle, a `finding` and the report says it does not check it.
4. A section "The Knowledge dogfood (card E9.17)" in `docs/dogfood.md`: who, what runs, when it starts (with the twin's, on the lead's go), setup, the commands, the known limits it shares with the twin's and the ones it adds, and a counts table like the twin's. Replace the last paragraph's "which no card covers yet ... The lead decides" with a pointer to it.
5. The profile's floors and counts are "proposed values"; list them for the lead's acceptance as the twin's were reviewed ("The twin profile's values"), as a precondition, not a change.
6. A `change` entry per deliverable and a `decision` per choice above.
