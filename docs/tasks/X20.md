# X20 A refused answer call is an exclusion; a key or credit error stops the run

Status: planned, gate work (2026-11-25). Pre-tag condition 3, first half (lead-decisions item 14).

From `docs/tasks/absorb-plan-2.md`, section 9, "Gate work cards (2026-11-25)". Lane: research. Week: W8, merged by 30 November. Effort: M. Read AGENTS.md, `docs/conventions/testing.md`, card RV1 and the pre-registration's Statistics section ("Seeds and exclusions") before starting.

Goal: When the provider refuses an answer call with an error no retry can fix (a prompt over the context limit, a 400), the runner records the session as excluded under its own reason, counted per condition, and goes on; an HTTP 401, 402 or 403 stops the run instead and is never a per-session exclusion. A replay excludes the same sessions the same way with zero calls.

Why: Pre-tag condition 3 says items 14 and 15 are built before the tag, and the Statistics section says this one is not. Today a non-transient answer failure ends the run: `sessionFailure` in `packages/runner/src/model/cassette.ts` returns it and each probe throws it (`gatemem-probe.ts`, line 478), so one over-long prompt would stop a multi-day H1 run (item 14's reason). The 401, 402 and 403 rule is the coordinator's decision of 2026-11-21 (`docs/log/2026-11-21-answers-decision-cap-in-billed-dollars.md`): a key or credit problem is the operator's to fix, and excluding every later session under it would empty the run.

Sources: pre-registration, pre-tag condition 3 and Statistics; `docs/tasks/lead-decisions.md`, item 14 and its row (a); backlog row "A refused answer call".

What already exists (checked on main at `09a1d85c`): the `excluded` field and its per-condition counts for `turn limit` in the GateMem, MEM-INV-Bench and LongMemEval probes (`excluded?: "turn limit"`, counted in each summary); the transient retry and `TransientCallError`, which stop a session unrecorded so a resume calls again (card RV1); the judge's recorded non-transient failure (`JudgeCallFailed`, `cachedJudgeCall`), the pattern to follow; the H1 converter's `exclusion` field (`packages/runner/src/research/h1-sessions.ts`, `research/analysis/h1.py`, schema `h1-sessions/2`), which already counts excluded sessions by reason.

Steps:

1. Tests first, on a fake provider that answers with a scripted error reply (no network): a 400 "context length" refusal excludes that session under one new reason (name it once, for example `answer refused`, in a `decision` entry), the next session runs, and the summary counts it per condition; a 401, a 402 and a 403 each stop the run with a message naming the status and no row for that session, and `RESUME=1` after the key is fixed runs it; a transient error that outlasts the retry still stops the session unrecorded (RV1's behaviour, unchanged); a replay of the excluding run excludes the same session from its cassette with zero calls.
2. Record a non-transient answer refusal in the cassette as the judge records its failure, so the replay is exact; classify 401, 402 and 403 before that, from the reply's error, and throw a stopping error that is never recorded.
3. Carry the reason through all three probes' `excluded` and summaries, and through the H1 converter (`packages/runner/src/research/h1-sessions.ts`) into the row's `exclusion`, so the H1 table counts it with the reasons it already counts.
4. Every failed attempt's usage still goes to the ledger (review RV1-3).
5. A `change` entry, a `decision` entry for the reason's name and for how a status is read from pi-ai's error message, and a `finding` if pi-ai's reply does not carry the status in a form the classifier can read reliably.
