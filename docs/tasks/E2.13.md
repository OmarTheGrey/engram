# E2.13 Who can read this memory

Status: open.

From `docs/tasks/absorb-plan.md`, pull request 24 of 30 (research plans R-082 in `docs/research/absorb/long-list.md`). Lane: product. Week: W15. Effort: M. Read AGENTS.md, the plan's entry for this card and `docs/conventions/absorption.md` before starting.

Goal: For any item or scope, the plane answers who can read it and why: a set of readers, each with the rule or grant that admits them, computed from the same rules that decide a read.

Why: It is the first question an owner asks before sharing anything, and the one every commercial governance product answers. Engram can answer it exactly, with no new dependency.

Steps:

1. `Plane.whoCanRead(scope)` and `Plane.whoCanReadItem(id)` in core, built on the functions the read path already uses, returning a symbolic set (for example, "every member of team:x", "person:a by grant until a date") with the reason for each entry.
2. A property test: on generated policies, memberships and grants, the symbolic answer expands to exactly the actors for whom `evaluateRead` allows the item.
3. Visibility: the call answers only for an actor who may read the item or who owns the scope, and names grant holders to the owner only. Anyone else gets the same refusal as for an item that does not exist.
4. A route, `engram who-can-read` through the generated client, and a panel on the inspector's item page. `make api`.

Absorbs (mode per ADR 0037):

- SpiceDB (Apache-2.0, idea): the shape of its LookupSubjects query.
- OpenFGA (Apache-2.0, idea): the shape of its Expand query.
