# E2.9 The secret and personal-data guard at the write gate

Status: open.

From `docs/tasks/absorb-plan.md`, pull request 14 of 30 (research plans R-027 in `docs/research/absorb/long-list.md`). Lane: research. Week: W12. Effort: M. Read AGENTS.md, the plan's entry for this card and `docs/conventions/absorption.md` before starting.

Goal: A write whose content holds a secret or personal data is denied or held as a candidate, as the policy says, with a reason that names the kind and never the value.

Why: The write gate checks who is writing and where, never what. An API key pasted into a conversation is stored and recalled like any other fact. About a dozen of the repositories read have such a guard, and every commercial competitor does.

Steps:

1. `secrets.ts`: a pure detector over content, driven by rule tables. Two tiers: BLOCK for a recognised secret or personal-data pattern, REVIEW for a high-entropy string or a hexadecimal run near a keyword.
2. A stage in `evaluateWrite` that reads `content_guards`: off does nothing, review holds the write as a candidate, block denies it. The event's reason names the rule's kind and a fingerprint of the first and last four characters, never the value or its position in a way that reveals it.
3. Validators that cut false positives: Luhn for card numbers, mod-97 for IBANs. An allowlist test over git hashes, UUIDs, content hashes and cloud action names.
4. A timeout test per rule against catastrophic backtracking; a rule that fails it is not admitted.
5. One shared table with the redactor in `packages/core/src/plane/bypass.ts`, so there is one list to maintain.
6. A research script that reports coverage on a synthetic secret set and the false-positive rate on a benign corpus, with a MANIFEST row. Redaction is not offered: it would change the content hash.
