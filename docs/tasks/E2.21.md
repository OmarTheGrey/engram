## Part 1, now (byte-neutral; tests only)

1. Item 35: after the owner's class-changing promotion, the grant the new version keeps admits the grantee nothing, through the real `Plane.promote` and the grantee's own `Plane.read`. The owner's promotion keeping the grant is already tested ("RV7-R1: the owner's own new version keeps the grants", `write-grants.test.ts`); not added again.
2. ADR 0046, decision 7: no surface exposes `replay`. The server's `POST /api/v1/promote` refuses a body carrying `replay` (400, the strict `PromoteRequest`) and the OpenAPI document offers no such field; `engram promote --replay` is bad usage (exit 2, nothing logged); no MCP tool promotes or takes a `replay`, over the default list and the list `engram mcp --supersede` serves, at any depth of a parameter schema; and no tool the pi extension registers promotes or takes a `replay`, collected from the extension itself (`packages/pi-extension/test/surface.test.ts`).

## Part 2, after H1's registered runs

Depends on: E2.14 of the second absorb plan (its schema PR, which collects that plan's policy options), and H1's `MERGE` (`make run CONFIG=research/configs/h1-gatemem.json ... MERGE=n`, then `h1-mem-inv.json`) being done on main. Do not start before both.

Steps:

1. The policy option `grants.expiry_cap`, added by E2.14's schema PR, absent by default, that turns on the two rules below. Absent, the write gate decides exactly as today. Part 2 lifts E2.14's loader refusal of the option (`packages/core/src/policy/load.ts`, with a loader test) and sets it in `packages/pi-package/profiles/twin.yaml` and `packages/pi-package/profiles/knowledge.yaml`, the lead's answer (`docs/log/2026-11-25-ans-2026-11-25-decision-grant-cap-opt-in.md`). No registered preset (strict, medium, permissive) and no `research/configs/` file sets it.
2. The cap. A grant's expiry is at most 365 days (31,536,000 seconds) after the write's own event time, the injected clock's `at` (core reads no clock). A longer expiry is refused, never clamped, under the policy id `engram/write/grant-expiry-cap`, with a reason naming the limit and the grant's expiry. Exactly 365 days lands; one second past it is refused. It applies to every grant a write lands: a first write, a rewrite that changes the grants, and `Plane.changeGrants`'s additions. A grant a rewrite keeps unchanged is not judged again.
3. The first-write rule. With the option on, a first write is held to the whole of `grantDefect`: an expired grant and a grant of another class are refused on a first write too (today `evaluateWrite`'s loop skips them: `if (!changesGrants || kept) continue;`).
4. The exemption. A promotion's new version is not judged as a first write for either rule (ADR 0034, decision 6): an owner's promotion keeps its grants as they stand.
5. The tests that change: "a grant naming another class than the item's is refused by a rewrite adding it and by a grant change" (`write-grants.test.ts`, lines 136 to 153 on 2026-11-27, its first-write half lines 146 to 152) and "a rewrite adding an expired grant is refused; a first write carrying one still lands" keep today's behaviour with the option absent and gain the option-on counterpart. New counterexample tests: the cap at 365 days and one second past it, a first write with an expired grant, a first write with another class, the promotion exemption; each mutation-checked.
6. The invariants' oracle (`packages/core/test/property/oracle.ts`, `writeForbidden`) judges the option the same way core does, and `make test-invariants` passes.
7. The fixtures and tests the profiles reach. With the option on in twin, `fixtures/profiles/twin-reads.json` write 4 (a first write at `at` 2026-10-25 carrying a grant that expired 2026-10-01) would be refused. Part 2 changes the fixture so the read-side case it exists for stays: write 4 takes its own write time (an optional per-write `at`, read by `packages/core/test/unit/profiles/twin.test.ts`) before 2026-10-01, so it lands with a live grant inside the cap, and the reads at the fixture's `at` still find it expired and return what they return today. The expired-grant refusal on a first write gets its own counterexample test (step 5), not a fixture write. Every other test file that loads `twin.yaml` or `knowledge.yaml` runs with the option on and must pass unchanged or be changed on purpose, each change named in the log: in core, `test/unit/plane/write-grants.test.ts`, `grants.test.ts`, `offboard.test.ts`, `offboard-edges.test.ts`, `crash-windows.test.ts`, `cross-handle.test.ts`, `cross-handle-review.test.ts`, `cross-handle-verify.test.ts`, `test/unit/oracle-grants.test.ts`, `dogfood-report.test.ts`, `dogfood-cross-handle.test.ts`, `test/unit/profiles/twin.test.ts`, `knowledge.test.ts`, `test/property/invariants.test.ts`, `stateful.test.ts`, `visible-events.test.ts`; in adapters, `test/plane/grants-files.test.ts`, `cross-handle-files.test.ts`, `rv4-files.test.ts`, `rv4-review.test.ts`, `version-zero-files.test.ts`; `packages/ui/test/workspace.ts`, `packages/ui/test/twin.test.ts`, `test/e2e/twin.e2e.test.ts` and `test/e2e/who-can-read.e2e.test.ts` (with `fixtures/workspaces/twin/`, loaded through `twinWorkspace()`); and `packages/core/scripts/dogfood-report.ts`, which replays a member's own log under the twin profile, so a grant a member wrote before part 2 beyond a year would read as a violation there (part 2 decides and logs how the report treats it). The read filter's tests that seed an expired grant or a grant of another class on a first write (`packages/core/test/unit/plane/read.test.ts`, "a grant expired or of another class reaches no item through the plane's matching" and "filtered counts items the reader could reach but that fail validity, status or a grant's terms"; `read-by-id.test.ts`, "an item reached only through a grant that does not admit it answers as an unknown id") seed under `testPolicy()`, which leaves the option absent, so they keep today's behaviour; part 2 checks that and says so.
