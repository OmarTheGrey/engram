Why: The ADR is accepted, so the code must meet it. So the rule waits, behind an option, until after H1's registered runs (`docs/log/2026-11-25-e2-21-decision-split-after-h1.md`).

## Part 1, now (byte-neutral; tests only)

1. Item 35: after the owner's class-changing promotion, the grant the new version keeps admits the grantee nothing, through the real `Plane.promote` and the grantee's own `Plane.read`. The owner's promotion keeping the grant is already tested ("RV7-R1: the owner's own new version keeps the grants", `write-grants.test.ts`); not added again.
2. ADR 0046, decision 7: no surface exposes `replay`. The server's `POST /api/v1/promote` refuses a body carrying `replay` (400, the strict `PromoteRequest`) and the OpenAPI document offers no such field; `engram promote --replay` is bad usage (exit 2, nothing logged); no MCP tool promotes or takes a `replay` (the MCP tools are the pi extension's own).

## Part 2, after H1's registered runs

Depends on: E2.14 of the second absorb plan (its schema PR, which collects that plan's policy options), and H1's `MERGE` (`make run CONFIG=research/configs/h1-gatemem.json ... MERGE=n`, then `h1-mem-inv.json`) being done on main. Do not start before both.

Steps:

1. A policy option, added by E2.14's schema PR, absent by default and set by no registered preset (strict, medium, permissive, twin as it stands), that turns on the two rules below. Absent, the write gate decides exactly as today.
2. The cap. A grant's expiry is at most 365 days (31,536,000 seconds) after the write's own event time, the injected clock's `at` (core reads no clock). A longer expiry is refused, never clamped, under the policy id `engram/write/grant-expiry-cap`, with a reason naming the limit. Exactly 365 days lands; one second past it is refused. It applies to every grant a write lands: a first write, a rewrite that changes the grants, and `Plane.changeGrants`'s additions. A grant a rewrite keeps unchanged is not judged again.
3. The first-write rule. With the option on, a first write is held to the whole of `grantDefect`: an expired grant and a grant of another class are refused on a first write too (today `evaluateWrite`'s loop skips them: `if (!changesGrants || kept) continue;`).
4. The exemption. A promotion's new version is not judged as a first write for either rule (ADR 0034, decision 6): an owner's promotion keeps its grants as they stand.
5. The tests that change: "a grant naming another class than the item's is refused by a rewrite adding it and by a grant change" (`write-grants.test.ts`, its first-write half, lines 135 to 153 on 2026-11-25) and "a rewrite adding an expired grant is refused; a first write carrying one still lands" keep today's behaviour with the option absent and gain the option-on counterpart. New counterexample tests: the cap at 365 days and one second past it, a first write with an expired grant, a first write with another class, the promotion exemption; each mutation-checked.
6. The invariants' oracle (`packages/core/test/property/oracle.ts`, `writeForbidden`) judges the option the same way core does, and `make test-invariants` passes.
7. `fixtures/profiles/twin-reads.json` writes an expired grant on a first write on purpose (write 4). If the twin profile turns the option on, the lead decides then whether that write becomes an expected refusal or the fixture changes.
