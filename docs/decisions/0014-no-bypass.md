# ADR 0014: No-bypass: store commands blocked in bash; MCP store tools wrapped

Status: accepted with amendments, 2026-11-02
Deciders: Omar (lead)
Supersedes: the proposal of the same number in `docs/decisions/README.md`

## Context

Invariant 2 is meaningless if an agent can write to the store from a shell; MPBench's write channels include tool outputs.

## Decision

The extension's `user_bash` and `tool_call` handlers block a configured list of store commands and endpoints (`mem0`, `letta`, direct file writes under adapter roots) and route them through the Engram tools. MCP tools that reach a store are wrapped so their calls pass the gate. A blocked bypass is an event.

Amendments made when deciding:

- Amended from S0.5: pi emits user_bash only for the user's `!` commands and only from its interactive and RPC hosts, so the model's bash tool is gated in tool_call with the same command list and the runner emits user_bash itself.
- user_bash cannot block a command, so a block is a replacement result with exit code 126, recorded as an event.

Amendments made in the review fix pass, 2026-10-25 (PR #7, findings R7-1 to R7-15):

- Decision D10 (finding R7-1): shell text cannot be parsed into a complete answer, so the check errs towards blocking. A command is a store command if any word of it, after removing quotes, a leading path, an executable suffix (`.exe`, `.cmd` and the like) and case, and on either side of an `=`, is a known store name (`mem0`, `letta`), wherever it stands: behind wrappers (env, sudo, exec, time, xargs, npx, uvx, `pnpm dlx`, `python -m`), inside `bash -c` and `sh -c` arguments, subshells, braces, `$()`, backticks, and after `&`, `;`, `|`, `&&`, `||`. The check runs for user_bash and for the model's bash and powershell tools. Mentions that would not run the store (`echo mem0`) are blocked too; that is the cost of erring this way.
- Decision D10: pi's file tools (read, write, edit, grep, find, ls) and any tool with a path argument are blocked, as a `Plane.recordBypass` event with policy_id `engram/bypass/store-path`, on a path that resolves inside a configured store root (realpath of the path or its nearest existing ancestor, else the normalised absolute path, without case on Windows). grep and find are also blocked when a root lies inside the directory they search. A shell command word that is such a path is blocked the same way.
- Limit, recorded as D10 asks: a store name that a variable, an alias, a function or a script supplies at run time (`$STORE add x`, `$(printf mem%s 0)`), and a shell command that reaches a root through a path it computes, are out of reach of any text check. The extension's header comment says the same; nothing more is claimed.
- Finding R7-9: `Plane.recordBypass` keeps what was attempted in the event's reason (`...; attempted: <command>`), on one line, cut to 160 characters, with values that look like secrets (`NAME_KEY=`, `--token`, `Bearer`, URL credentials, `sk-` and long key-like strings) replaced by `<redacted>`. It refuses an invalid actor, time or bypass with `InvalidCallError`, as every other Plane call does (decision D6). A bypass has a route: `command` (`engram/bypass/store-command`), `path` (`engram/bypass/store-path`) and `result` (`engram/bypass/foreign-result`, decision D11, see ADR 0009).

Amendments made in the second review round, 2026-10-29 (PR #7, verifier report defects 1, 2 and 4):

- Defect 1: shell text is normalised as a shell reads it before the word check: a backslash-newline continuation is joined, `$'...'` quoting is decoded, cmd's `^` escape is dropped, and brace expansion (`me{m,}0`, `mem{0..1}`, nested groups) is expanded. Each word is also read with C escapes decoded (printf, `echo -e`), with `+` removed (`'me'+'m0'`), with PowerShell's backtick escape removed, split at `:` (`${X:-mem0}`) and at `@` (`mem0@latest`), and without leading dashes or `!`. A word with glob characters and at least two literal characters is matched as a pattern against the store names (`mem?`, `mem*`, `m[e]m0`). Still out of reach, and not claimed: a name assembled at run time (`$(printf mem%s 0)`, `x=me; ${x}m0`), a glob with fewer than two literal characters (`m*`, `*`), and lookalike letters of another alphabet.
- Defect 2: on Windows, a Git Bash, MSYS, Cygwin or WSL drive path (`/c/x`, `/cygdrive/c/x`, `/mnt/c/x`) is read as `C:\x` before the store-root check, in shell commands and in file tool arguments, as pi's own tools read it. File tool arguments are also resolved the rest of the way pi resolves them (unicode spaces, `file://` URLs), and the path as written is checked as well.
- Defect 4: "any tool with a path argument" now means: every string under a key that names a path (`path`, `file`, `dir`, `src`, `target`, `dest` and the like) at any depth of the arguments, and every one-line string anywhere in them that is a path on its own (absolute, `~/`, `./`, `../`, a `file://` URL). A relative path inside other free text (an edit's old text, a file's new content, a search pattern) is not read as a path, to avoid blocking ordinary edits that mention one; a hard link to a store file from outside the root is not seen either.

Amendments made in card E2.5's verification, 2026-10-29 (review findings P5-2 and P5-18):

- `engram` is a store command: the Engram CLI takes `--as` and `--member` as given, so a model running it could write, confirm and approve as anyone (ADR 0026's amendments). It is blocked by name, and by its other routes: the package spec `@engram/cli` (npx, `pnpm dlx`, `pnpm --filter`, with or without a version) and the workspace folder `packages/cli` (its entry script `packages/cli/src/main.ts`, `cd` into the folder, `--filter ./packages/cli`); real-session tests in packages/pi-extension/test/engram-cli-block.test.ts. The cost: inside a pi session in this repository, any command naming `packages/cli` (running its tests, say) is refused too.
- The text check's limit is the one stated for the store names: it does not reach the CLI through a name assembled at run time, an alias or a script defined outside the command, a copy of the entry script elsewhere, a shell started from another program, or an installed binary under another name. The CLI's identity limit itself is a stated limit of ADR 0026, not something this check removes.

Amendments made in PR 3 of the plan (card E8.4; branch gb-pr3-surfaces, 2026-10-29):

- The store-command check and the store-root check move from packages/pi-extension (bash.ts and paths.ts, now re-exports) to core (packages/core/src/no-bypass.ts, no-bypass/shell.ts, no-bypass/paths.ts), because they decide (AGENTS.md rule 1). `shellBypass` and `toolBypass` return the bypass a surface records; the pi extension and the Claude Code hook (`engram hook claude-code`, ADR 0022) both call them. The pi extension's tests pass unchanged.
- Review finding P5-20 (backlog, "CLI path spellings in pi bash"): each word is also read as a normalised path, so `packages//cli`, `packages/./cli` and `packages/x/../cli` are blocked; `../cli` (the folder from a sibling package) and `cli/src/main.ts` under any prefix are blocked too. The cost: any other folder named `cli` reached as `../cli`, and any `cli/src/main.ts`, is refused. Still out of reach: a path a command computes at run time, and a pnpm filter by bare package name.
- Review fix pass of PR 3 (finding R3-7): `notebook_path` (NotebookEdit) is a path key; every shell word is resolved against the cwd, not only words that look like paths, so a bare root name (`cd memory && cat a.md`) is caught; a word with glob characters is caught when, resolved against the cwd, each of its segments matches the root's segment at that depth (`memor*/a.md`, `mem?ry`, `mem[o]ry`); and on Windows a path through the machine's own admin share or a device prefix (`\\localhost\C$\...`, `\\127.0.0.1\C$\...`, `\\?\C:\...`, `\\.\C:\...`) is read as its drive path. Verification follow-ups (findings R3-15 to R3-18): every word of every quoted argument is checked, as at the first fix pass, since a quoted string can be a script run by `eval`, `bash <<<`, a pipe into a shell, `iex` or `Invoke-Expression`, `python -c` or `node -e`. The one exception, shrunk to its smallest safe form in the last verification rounds (findings R3-19 to R3-25), is a commit message, read as one word with only its path-like words checked, when all of these hold: it is wholly single-quoted (`-m '...'`, `--message '...'` or `--message='...'`); the tool (`git`, `hg`, `svn`, `jj`, `bzr`) is in command position, first in its list or pipeline segment (an unquoted `;`, `&`, `|` or newline ends one) or right after a wrapper (`env` with assignments, `sudo`, `doas`, `xargs`, `nohup`, `nice`, `time`, `timeout` and its duration, `command`, `exec`); and its subcommand, the first non-option words after the tool with `-c key=val` and `-C dir` skipped, is a built-in that takes a message (git `commit`, `tag`, `merge`, `notes`, `stash push`, `stash save`; hg `commit`, `tag`; svn `commit`, `ci`; jj `commit`, `describe`, `new`; bzr `commit`). An exempt message must be single-quoted because a single-quoted word never expands: no command substitution, backtick, process substitution or parameter expansion can run inside it, which removes by construction every hole the double-quoted rule kept growing (`$(cd memory; cat a.md)` in a message). Single quotes protect only against the shell that reads them, so (finding R3-26) the exemption is also withheld wherever an outer shell expands first: inside a nested script argument unless every enclosing script argument was itself wholly single-quoted (`bash -c 'git commit -m "x"'` keeps it; `bash -c "git commit -m '...'"` loses it), inside a decoded PowerShell command, and anywhere in a command that holds a heredoc of any kind, that is any `<<` other than a here-string `<<<`, whatever its delimiter (finding R3-27: `<<!`, `<<.` and `<<$X` expand their bodies too, and telling an expanding delimiter from a quoted one proved error-prone, so `<<'EOF'` loses the exemption as well). An alias, or any other subcommand, gets no exemption, since an alias can evaluate its arguments (`git -c alias.y='!f(){ eval "$2"; }; f' y -m "..."`). The cost: `git commit -m "fix memory leak"` (double-quoted) is refused when a root is named `memory`; write the message in single quotes. Every word is also read as a path after its first colon and, on the raw word before brace expansion, after its last colon, so `git show HEAD:memory/a.md`, `git show :memory/a.md`, `git show :0:memory/a.md`, `git show stash@{0}:memory/a.md` and `git cat-file -p HEAD:memory/a.md` are refused. A shell's script argument (`bash`, `sh`, `zsh`, `dash`, `ksh`, `ash` or `fish` after a `-c` flag such as `-c` or `-lc`, also after `--`; `pwsh` or `powershell` after `-c` or `-Command`; `cmd` after `/c` or `/k`) is checked recursively as a nested command, up to eight levels, and a PowerShell `-EncodedCommand` (`-e`, `-ec`, `-enc` and the other prefixes; base64 of UTF-16LE) is decoded and checked the same way, store names included. The false positives kept on purpose, erring towards blocking: any word naming a root beside the cwd, quoted or not, outside a version-control message (`echo memory`, `grep -rn memory src`, `grep -rn "memory leak" src`, `ls memory`); `ls *` and `rm -rf *` when a root sits in the cwd, and every command whose cwd is inside a root, which do reach the store. Still out of reach: another host name for this machine in a UNC path (its network name or IP), a command that reaches a store from an enclosing folder without naming it (`rm -rf .`, `find . -exec cat {} +`, `grep -r x .`, `git log -p` and `git show` with no path, from the folder or repository that holds the root: only file tools that search a tree are checked for a root inside their path), removing the project folder or the home folder as a whole, which takes a store root inside it along (the hook guards only folders strictly inside them), a symlink or junction created at run time, a glob that only matches the root's parent (`rm -r ./*` with the root one level down is caught only when the pattern reaches the root's depth), brace or variable expansion that assembles a root name at run time, and environment variables (`%USERPROFILE%`, `$HOME`) inside paths.

Amendments made by card RV3, 2026-11-19 (repository review findings RV-ADP-7 and RV-ADP-8). Status: proposed, for the lead's acceptance.

- RV-ADP-7: the machine's own loopback names in a UNC path are now `localhost`, any 127.0.0.0/8 address (in full or short dotted form, `127.1`), IPv6's `[::1]` (any spelling of its zeros) and its UNC literal `0--1.ipv6-literal.net`, and the device namespace's `\\?\UNC\<host>\` and `\\.\UNC\<host>\` are read as `\\<host>\`. So `\\?\UNC\localhost\C$\...`, `\\.\UNC\localhost\C$\...`, `\\[::1]\C$\...` and `\\0--1.ipv6-literal.net\C$\...` are read as their drive paths, in file tool arguments and in shell commands, for pi and for the Claude Code hook (`packages/core/src/no-bypass/paths.ts`, `LOOPBACK_HOST` and `uncDrivePath`). In a shell command any run of separators stands for one and the share's `$` may be escaped (`\$`), because a posix shell reads `\\` as one backslash: the command text that reaches `\\localhost\C$\x` from Git Bash, Claude Code's Bash tool on Windows, is `\\\\localhost\\C$\\x`, which the check missed for every loopback host, `\\localhost` included, before this card's review fix pass (RV3-2; run in Git Bash on a scratch store, six of the eight spellings reached it on this machine, and all eight are now refused). Still out of reach, as stated above: the machine's network name or another of its addresses.
- RV-ADP-8: Letta Code's CLI is also reached as its npm package `@letta-ai/letta-code`, whose binary is `letta` (npm registry metadata, read 2026-11-19), with or without a version; the word is blocked as a route of the `letta` store, as `@engram/cli` is of `engram`.

Amendments proposed by card RV5, 2026-11-20 (findings RV-SRF-3 and RV-SRF-4 of the repository review of the surfaces). Status: proposed, for the lead's acceptance; drafted by the card's agent.

- RV-SRF-3: the pi extension guards the files that govern its session, as the Claude Code hook guards its own (finding R3-2). `createEngramExtension` takes `protect` (files and folders) and `protectBelow` (the folders below which a folder holding one is guarded too, R3-13), checked with the same core functions as a store root and reported as store `engram` (`engram/bypass/store-path`). The pi package fills them: the log when it is a SQLite file, with its `-wal`, `-shm` and `-journal` files; the project's `.pi/` folder (settings, extensions, prompt templates); and pi's agent folder (`getAgentDir()`, by default `~/.pi/agent`), below the project and the home folder. Reproduced before: pi's `write` tool overwrote the log and `bash rm` deleted it.
- RV-SRF-4: only the four tools the extension registers (`memory_write`, `memory_read`, `memory_explain`, `memory_simulate`) skip the no-bypass checks in `tool_call`. Before, every tool whose name began with `memory_` skipped them, so another extension's `memory_export` wrote into a store root and no bypass was recorded. The context handler still withholds every `memory_*` result the extension did not produce (decision D11).

Amendment made by card RV7, 2026-11-20 (core review finding RV-CORE-5). Status: proposed, for the lead's acceptance.

- Folders a command moves to: every word of a shell command is also resolved against every folder a `cd`, `pushd`, `chdir`, `Set-Location` or `sl` (options and cmd's `/d` skipped), a `-C dir` (git, make, tar) or a `--directory dir` or `--directory=dir` names in it, each resolved against the cwd and every folder named before it, and a bare `cd` adds the home folder (`workingDirs` in `packages/core/src/no-bypass.ts`). So `cd .. && cat mem/a.md`, `cd /home/u; cat mem/a.md`, `tar cf - -C /home/u mem` and `git -C .. show HEAD:mem/a.md` are refused. The text is read as written, nested scripts and quotes included, at most 32 folders; a `cd` inside a single-quoted `-m` or `--message` is ignored, since such a message never runs.
- Recursive walks: when the command holds a tree walker (`find`, `rg`, `ag`, `ack`, `fd`, `tree`, `du`, `tar`, `rsync`) or a command that walks under a flag (`grep`, `egrep`, `fgrep` and `rm` with `-r` or `-R`, `cp` with `-r`, `-R` or `-a`, `ls`, `chmod`, `chown` and `chgrp` with `-R`, `scp`, `zip` and `diff` with `-r`, PowerShell's `Get-ChildItem`, `gci`, `dir`, `Remove-Item` and `Copy-Item` with `-r` or `-Recurse`, and `--recursive` or `--archive` anywhere), every word is also a hit when a store root lies inside the folder it names, as for pi's grep and find tools: `grep -r secret /home/u`, `find /home/u -name a.md -exec cat {} +`, `grep -r x .` from the folder holding the root. This applies to store roots only; a protected file's folders keep the rule of R3-13 (strictly below the given folders), so a walk over the project is no hit for `.claude/settings.json`.
- `~user` is read as the folder `user` beside the home folder (`expandHome` in `packages/core/src/no-bypass/paths.ts`), for shell words and tool paths alike.
- Costs, erring towards blocking: both rules judge the whole command, not one segment, so a word is also resolved against folders the command enters only after it, and a walker anywhere makes every word judged as walked (`grep -r x src; cat ..` is refused when the root sits beside the cwd).
- Limits, still out of reach: a walk with no path from the folder holding a root (`find`, `rg x`, `grep -r x` with no file, `git log -p`), which would refuse every such walk in a project holding a root; a folder named through a variable (`cd $HOME`), `cd -`, `~+` and `~-`; a user whose home folder is not beside the current one; a `cd` hidden in a single-quoted commit message of a git alias that evaluates it.
- Review fix pass of PR #61 (findings RV7-R3 and RV7-R7). Also followed now: `cd --`, a command name quoted or escaped (`\cd`, `"cd"`, `c''d`, and `builtin cd`), PowerShell's `Push-Location`, `-C` with its folder attached (`make -C..`, `tar -C..`) and `env -C` or `--chdir`. A single-quoted `-m` or `--message` is set aside only after `git`, `hg`, `svn`, `jj` or `bzr` in command position, so `bash -c -m 'cd ..; ...'` is read as the script it is. A chain of literal `cd dir &&` at the very start of a command replaces the cwd only when everything after the chain is joined by `&&` and pipes alone, with no `;`, `||`, single `&` or newline outside quotes (and no `$(` or backtick inside double quotes), so every later word runs in `dir` or not at all and `cd src && grep -r TODO .` is judged in `src` alone; after any of those separators a word still runs in the old folder when the `cd` failed, so `cd nope && ls; cat mem/a.md` keeps the cwd (second review pass, RV7-R7b); a `cd` anywhere else, or one whose folder holds `$`, a backtick or a glob, still adds folders and keeps the cwd. On the reviewer's 39 ordinary commands none is refused with the root beside the repository or in Claude Code's memory folder; with the root inside the repository, 7 are, each a walk over `.` (`grep -rn TODO .`, `rg foo .`, `find . -name '*.ts'`, `tar czf all.tgz .`, `du -sh .`, `tree -L 2 .`, `find . -type f`), which does reach it. Still refused at a cost: `cd src; grep -r TODO .` (a `;` does not make the cwd go). Still out of reach, besides the limits above: a folder held in a variable or built by a substitution (`cd $D`, `cd "$(dirname "$PWD")"`), `cd -`, a program that changes its own folder (`python -c "os.chdir(...)"`, `node -e "process.chdir(...)"`), and `xargs` running a command on paths it builds (`ls .. | xargs -I{} cat ../{}/a.md`).

No alternatives were recorded beyond the recommendation.

## Consequences

Unblocks PX1, Gate A check. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.
