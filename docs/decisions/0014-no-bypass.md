# ADR 0014: No-bypass: store commands blocked in bash; MCP store tools wrapped

Status: accepted with amendments, pending lead review, 2026-10-22
Deciders: drafted by the coding agent in step-0 task S0.13; pending review and acceptance by Omar (lead). Until then this records a recommendation the code already follows.
Supersedes: the proposal of the same number in `docs/decisions/README.md`

## Context

Invariant 2 is meaningless if an agent can write to the store from a shell; MPBench's write channels include tool outputs.

## Decision

The extension's `user_bash` and `tool_call` handlers block a configured list of store commands and endpoints (`mem0`, `letta`, direct file writes under adapter roots) and route them through the Engram tools. MCP tools that reach a store are wrapped so their calls pass the gate. A blocked bypass is an event.

Amendments made when deciding:

- Amended from S0.5: pi emits user_bash only for the user's `!` commands and only from its interactive and RPC hosts, so the model's bash tool is gated in tool_call with the same command list and the runner emits user_bash itself.
- user_bash cannot block a command, so a block is a replacement result with exit code 126, recorded as an event.

Amendments made in the review fix pass, 2026-10-25 (PR #7, findings R7-1 to R7-15; pending the lead's review like the rest of this ADR):

- Decision D10 (finding R7-1): shell text cannot be parsed into a complete answer, so the check errs towards blocking. A command is a store command if any word of it, after removing quotes, a leading path, an executable suffix (`.exe`, `.cmd` and the like) and case, and on either side of an `=`, is a known store name (`mem0`, `letta`), wherever it stands: behind wrappers (env, sudo, exec, time, xargs, npx, uvx, `pnpm dlx`, `python -m`), inside `bash -c` and `sh -c` arguments, subshells, braces, `$()`, backticks, and after `&`, `;`, `|`, `&&`, `||`. The check runs for user_bash and for the model's bash and powershell tools. Mentions that would not run the store (`echo mem0`) are blocked too; that is the cost of erring this way.
- Decision D10: pi's file tools (read, write, edit, grep, find, ls) and any tool with a path argument are blocked, as a `Plane.recordBypass` event with policy_id `engram/bypass/store-path`, on a path that resolves inside a configured store root (realpath of the path or its nearest existing ancestor, else the normalised absolute path, without case on Windows). grep and find are also blocked when a root lies inside the directory they search. A shell command word that is such a path is blocked the same way.
- Limit, recorded as D10 asks: a store name that a variable, an alias, a function or a script supplies at run time (`$STORE add x`, `$(printf mem%s 0)`), and a shell command that reaches a root through a path it computes, are out of reach of any text check. The extension's header comment says the same; nothing more is claimed.
- Finding R7-9: `Plane.recordBypass` keeps what was attempted in the event's reason (`...; attempted: <command>`), on one line, cut to 160 characters, with values that look like secrets (`NAME_KEY=`, `--token`, `Bearer`, URL credentials, `sk-` and long key-like strings) replaced by `<redacted>`. It refuses an invalid actor, time or bypass with `InvalidCallError`, as every other Plane call does (decision D6). A bypass has a route: `command` (`engram/bypass/store-command`), `path` (`engram/bypass/store-path`) and `result` (`engram/bypass/foreign-result`, decision D11, see ADR 0009).

Amendments made in the second review round, 2026-10-29 (PR #7, verifier report defects 1, 2 and 4; pending the lead's review like the rest of this ADR):

- Defect 1: shell text is normalised as a shell reads it before the word check: a backslash-newline continuation is joined, `$'...'` quoting is decoded, cmd's `^` escape is dropped, and brace expansion (`me{m,}0`, `mem{0..1}`, nested groups) is expanded. Each word is also read with C escapes decoded (printf, `echo -e`), with `+` removed (`'me'+'m0'`), with PowerShell's backtick escape removed, split at `:` (`${X:-mem0}`) and at `@` (`mem0@latest`), and without leading dashes or `!`. A word with glob characters and at least two literal characters is matched as a pattern against the store names (`mem?`, `mem*`, `m[e]m0`). Still out of reach, and not claimed: a name assembled at run time (`$(printf mem%s 0)`, `x=me; ${x}m0`), a glob with fewer than two literal characters (`m*`, `*`), and lookalike letters of another alphabet.
- Defect 2: on Windows, a Git Bash, MSYS, Cygwin or WSL drive path (`/c/x`, `/cygdrive/c/x`, `/mnt/c/x`) is read as `C:\x` before the store-root check, in shell commands and in file tool arguments, as pi's own tools read it. File tool arguments are also resolved the rest of the way pi resolves them (unicode spaces, `file://` URLs), and the path as written is checked as well.
- Defect 4: "any tool with a path argument" now means: every string under a key that names a path (`path`, `file`, `dir`, `src`, `target`, `dest` and the like) at any depth of the arguments, and every one-line string anywhere in them that is a path on its own (absolute, `~/`, `./`, `../`, a `file://` URL). A relative path inside other free text (an edit's old text, a file's new content, a search pattern) is not read as a path, to avoid blocking ordinary edits that mention one; a hard link to a store file from outside the root is not seen either.

Amendments made in card E2.5's verification, 2026-10-29 (review findings P5-2 and P5-18; pending the lead's review like the rest of this ADR):

- `engram` is a store command: the Engram CLI takes `--as` and `--member` as given, so a model running it could write, confirm and approve as anyone (ADR 0026's amendments). It is blocked by name, and by its other routes: the package spec `@engram/cli` (npx, `pnpm dlx`, `pnpm --filter`, with or without a version) and the workspace folder `packages/cli` (its entry script `packages/cli/src/main.ts`, `cd` into the folder, `--filter ./packages/cli`); real-session tests in packages/pi-extension/test/engram-cli-block.test.ts. The cost: inside a pi session in this repository, any command naming `packages/cli` (running its tests, say) is refused too.
- The text check's limit is the one stated for the store names: it does not reach the CLI through a name assembled at run time, an alias or a script defined outside the command, a copy of the entry script elsewhere, a shell started from another program, or an installed binary under another name. The CLI's identity limit itself is a stated limit of ADR 0026, not something this check removes.


Amendments made in PR 3 of the plan (card E8.4; branch gb-pr3-surfaces, 2026-10-29; pending the lead's review like the rest of this ADR):

- The store-command check and the store-root check move from packages/pi-extension (bash.ts and paths.ts, now re-exports) to core (packages/core/src/no-bypass.ts, no-bypass/shell.ts, no-bypass/paths.ts), because they decide (AGENTS.md rule 1). `shellBypass` and `toolBypass` return the bypass a surface records; the pi extension and the Claude Code hook (`engram hook claude-code`, ADR 0022) both call them. The pi extension's tests pass unchanged.
- Review finding P5-20 (backlog, "CLI path spellings in pi bash"): each word is also read as a normalised path, so `packages//cli`, `packages/./cli` and `packages/x/../cli` are blocked; `../cli` (the folder from a sibling package) and `cli/src/main.ts` under any prefix are blocked too. The cost: any other folder named `cli` reached as `../cli`, and any `cli/src/main.ts`, is refused. Still out of reach: a path a command computes at run time, and a pnpm filter by bare package name.
- Review fix pass of PR 3 (finding R3-7): `notebook_path` (NotebookEdit) is a path key; every shell word is resolved against the cwd, not only words that look like paths, so a bare root name (`cd memory && cat a.md`) is caught; a word with glob characters is caught when, resolved against the cwd, each of its segments matches the root's segment at that depth (`memor*/a.md`, `mem?ry`, `mem[o]ry`); and on Windows a path through the machine's own admin share or a device prefix (`\\localhost\C$\...`, `\\127.0.0.1\C$\...`, `\\?\C:\...`, `\\.\C:\...`) is read as its drive path. Verification follow-ups (findings R3-15 to R3-18): every word of every quoted argument is checked, as at the first fix pass, since a quoted string can be a script run by `eval`, `bash <<<`, a pipe into a shell, `iex` or `Invoke-Expression`, `python -c` or `node -e`. The one exception, shrunk to its smallest safe form in the last verification rounds (findings R3-19 to R3-25), is a commit message, read as one word with only its path-like words checked, when all of these hold: it is wholly single-quoted (`-m '...'`, `--message '...'` or `--message='...'`); the tool (`git`, `hg`, `svn`, `jj`, `bzr`) is in command position, first in its list or pipeline segment (an unquoted `;`, `&`, `|` or newline ends one) or right after a wrapper (`env` with assignments, `sudo`, `doas`, `xargs`, `nohup`, `nice`, `time`, `timeout` and its duration, `command`, `exec`); and its subcommand, the first non-option words after the tool with `-c key=val` and `-C dir` skipped, is a built-in that takes a message (git `commit`, `tag`, `merge`, `notes`, `stash push`, `stash save`; hg `commit`, `tag`; svn `commit`, `ci`; jj `commit`, `describe`, `new`; bzr `commit`). An exempt message must be single-quoted because a single-quoted word never expands: no command substitution, backtick, process substitution or parameter expansion can run inside it, which removes by construction every hole the double-quoted rule kept growing (`$(cd memory; cat a.md)` in a message). An alias, or any other subcommand, gets no exemption, since an alias can evaluate its arguments (`git -c alias.y='!f(){ eval "$2"; }; f' y -m "..."`). The cost: `git commit -m "fix memory leak"` (double-quoted) is refused when a root is named `memory`; write the message in single quotes. Every word is also read as a path after its first colon and, on the raw word before brace expansion, after its last colon, so `git show HEAD:memory/a.md`, `git show :memory/a.md`, `git show :0:memory/a.md`, `git show stash@{0}:memory/a.md` and `git cat-file -p HEAD:memory/a.md` are refused. A shell's script argument (`bash`, `sh`, `zsh`, `dash`, `ksh`, `ash` or `fish` after a `-c` flag such as `-c` or `-lc`, also after `--`; `pwsh` or `powershell` after `-c` or `-Command`; `cmd` after `/c` or `/k`) is checked recursively as a nested command, up to eight levels, and a PowerShell `-EncodedCommand` (`-e`, `-ec`, `-enc` and the other prefixes; base64 of UTF-16LE) is decoded and checked the same way, store names included. The false positives kept on purpose, erring towards blocking: any word naming a root beside the cwd, quoted or not, outside a version-control message (`echo memory`, `grep -rn memory src`, `grep -rn "memory leak" src`, `ls memory`); `ls *` and `rm -rf *` when a root sits in the cwd, and every command whose cwd is inside a root, which do reach the store. Still out of reach: another host name for this machine in a UNC path (its network name or IP), a command that reaches a store from an enclosing folder without naming it (`rm -rf .`, `find . -exec cat {} +`, `grep -r x .`, `git log -p` and `git show` with no path, from the folder or repository that holds the root: only file tools that search a tree are checked for a root inside their path), removing the project folder or the home folder as a whole, which takes a store root inside it along (the hook guards only folders strictly inside them), a symlink or junction created at run time, a glob that only matches the root's parent (`rm -r ./*` with the root one level down is caught only when the pattern reaches the root's depth), brace or variable expansion that assembles a root name at run time, and environment variables (`%USERPROFILE%`, `$HOME`) inside paths.

No alternatives were recorded beyond the recommendation.

## Consequences

Unblocks PX1, Gate A check. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.
