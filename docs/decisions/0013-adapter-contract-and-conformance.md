# ADR 0013: Adapter contract with capability flags; conformance suite on a fake first

Status: accepted with amendments, 2026-11-02
Deciders: Omar (lead)
Supersedes: the proposal of the same number in `docs/decisions/README.md`

## Context

The stores differ in what they do natively: Mem0 (extract and update with ADD, UPDATE, DELETE, NOOP; history endpoint; graph variant), Letta (memory blocks plus archival; TypeScript client), Zep (native bi-temporal), files (nothing). The plane must respect a native feature rather than duplicate it.

## Decision

`Adapter` with `read`, `write`, `delete`, `list`, `search?`, `history?` and `capabilities: {native_validity, native_history, native_search, native_graph}`. `store_ref` is opaque. A complete in-memory fake passes the full conformance suite; real stores run the same suite in CI service containers. Mem0 through its TypeScript OSS package, Letta through `@letta-ai/letta-client`, files through the filesystem.

Amendments made when deciding:

- Implemented in S0.11: the contract is asynchronous; a write is idempotent per item id; a ref from another adapter is refused; the conformance suite is the exported function `conformance(name, factory)`; a capability claiming native search or history requires the method.

Amendments made in the review fix pass, 2026-10-25 (PR #4, findings R4-1 to R4-16):

- Fidelity: `read`, `list`, `search` and `history` return exactly the item written, every field deep-equal (grants, validity window, ttl, lineage, optional provenance fields, JSON content, content of any length, any Unicode including CRLF and a lone surrogate), with `store_ref` set to the ref the write returned. The suite compares whole items on every hit, and a committed meta-test (`packages/adapters/test/conformance/meta.test.ts`) requires each of twelve deliberately broken adapters to fail at least one case.
- Refs (orchestrator decision D1): several versions may live under one ref, which is the same item id rewritten (`history`); two distinct item ids get two refs, because both must stay readable. A rewrite that changes only `status` is stored.
- `list(scope)` matches the scope exactly; a prefix of a scope name, or a sibling such as `team:platform-x`, never matches.
- A foreign ref is refused by a rejected promise, never a synchronous throw, for `read`, `delete` and `history`; a refused delete deletes nothing.
- Concurrent writes of one item id leave one item under one ref; an adapter serialises its own writes when the store cannot (Mem0 does).
- `native_search` means the store searches by itself (an index or embeddings, the sense ADR 0018 relies on). An adapter may offer `search` without the flag: the files adapter scans the folder and now declares `native_search: false`, matching "files (nothing)" above.
- Files adapter: only regular files directly in the root are read or listed (symlinks, junctions and directories are skipped and refused); a malformed file is skipped by `list` and `search` and reported by `diagnostics()`, while `read` of it still throws; item ids must be lowercase and a name that differs only in case is refused; every write and delete holds `.engram.lock` in the root; Engram's index lines use " - ", and Claude Code's own lines are left as written.
- Mem0 adapter: `dbPath` is ":memory:" or a file ending in `.db`, and a file store writes `<name>_entities.db` beside it; telemetry is off whatever the import order; Mem0's model slot is replaced by one that refuses every call.

Amendments made in review round 2, 2026-10-28 (PR #4, verifier report V4):

- Fidelity also covers confidence at 0 and at 1, a lineage of several entries in the order written (neither sorted nor reversed), content with leading and trailing whitespace, a `role:` scope and an episodic item; the corpus holds each.
- `search` returns matching items whatever their status: candidate and retired items are found like active ones, because status is the plane's read filter, not the store's.
- The meta-test pins each broken adapter (now nineteen) to the cases it must fail, by name.
- Files adapter: a hard link (a file with more than one name) is treated like a symlink: skipped and reported by list and search, refused by read, write and delete, and MEMORY.md is refused when it is one. The earlier claim that nothing outside the root is followed held for symlinks and junctions only.
- Files adapter: a write or delete is all or nothing. MEMORY.md is checked before the item file changes, and if the index update fails anyway, the item file is removed or its previous bytes restored.
- Files adapter: the lock file records the holder's pid, host, a per-instance token and the wall-clock time (the adapter has no injected clock; the time is a fact of store I/O, not a policy input). A waiter breaks a lock whose pid is not alive on this machine, or that is older than 60 s; otherwise it waits up to `lockWaitMs` (default 10 s) and refuses, naming the holder. `lockSeams` (a clock and two hooks, defaulting to the wall clock and no-ops) exists only so tests can stage the lock's races.
- Mem0 adapter: the placeholder model in Mem0's config fails with its own error, distinct from the refusal of the replaced model slot, so a test shows the replacement is in place.

Amendments made in the review fix pass, round 2, 2026-10-29 (PR #6):

- Two optional methods. `diagnostics()` lists, by key, the entries the latest `list` or `search` skipped because the store cannot read them (the files adapter already had it; it is now part of the contract, as `StoreDiagnostic`). `derivedFields(item)` names the fields of a listed item that the store derived from its own bookkeeping rather than stored with the item. Neither is required, and the conformance suite does not test them; adoption (ADR 0007) uses both when present.
- Files adapter: a file without Engram metadata keeps `valid_from` from its modification time when `importValidFrom` is not given, and `derivedFields` reports `["valid_from"]` for it; for a file Engram wrote, or with `importValidFrom`, it reports none. So touching a file is not a new version of its memory. The alternative, a stable `valid_from` inside the adapter, was rejected: the adapter keeps no state and reads no clock, and the file's birth time is not portable (some file systems report the change time or the epoch instead), so no stable value carries the information the modification time does. Deciding in adoption keeps the adapter's item as it is and moves no store-specific rule into core.

Amendments made by the Gate B plan, 2026-10-29 (`docs/tasks/gate-b-plan.md`, decision 2):

- Letta is reached through MemFS, its git-backed context repository on local disk, not through `@letta-ai/letta-client` and a Letta server (ADR 0028). The server needs Docker or a hosted account; card A2 already named the git-backed files.

Amendments made by card RV3, 2026-11-19 (the repository review of the adapters, findings RV-ADP-1 to RV-ADP-10). Status: proposed, for the lead's acceptance; drafted by the card's agent.

- Files adapter, an Engram file is tied to its name (RV-ADP-1): a file whose `engram.id` is not its file name (a copy, a rename, a file written by hand) is refused, as the Letta adapter's `parseItem` refuses one. `list` and `search` skip it and name it in `diagnostics()`; `read` and `delete` throw `UnreadableItemError`. This stops copies and mismatched names, not forgery: a file written by hand under the name of its own new id, with Engram metadata and grants, is still read and adopted with its grants; that is RV-ADP-4, deferred to card RV4 (review fix pass, RV3-5). Before, a copy listed the id twice, every adoption of an unchanged folder appended events, and after a rewrite the stale copy's adoption retired the governed version.
- Files adapter, imported ids (RV-ADP-2): the id of a file without Engram metadata is derived from the folder's identity (its real path, without case on Windows) and the file name, not from the file name alone. The review proposed the owner and the file name; that was not taken, because adoption refuses an erased record by item id (`engram/adopt/erased`, ADR 0010), so an owner-derived id would let a successor adopting a leaver's unchanged folder under another owner take back the erased content (`packages/adapters/test/plane/offboard-files.test.ts`). The ids of imported files change at this card; no dogfood log exists yet, so nothing is migrated. Moving a folder changes its imported ids at the same refs (`files/<name>.md`), and core refuses a second item at a ref, a retired holder included (`refProblem` in `packages/core/src/plane/write.ts`), before adoption retires what the store no longer lists. Until card RV4, after a move every adoption, and every `engram read`, which adopts first, failed closed: one `engram/write/store-failure` deny event per attempt, nothing adopted or retired (review fix pass, RV3-1). Card RV4 removed the limit in core (amendment below): the moved files are adopted under their new ids and the old ids retired, and moving back recovers the same way (`packages/adapters/test/plane/rv3-files.test.ts`, `packages/adapters/test/plane/rv4-files.test.ts`). One log holding two folders also needs two adapter names, for the same reason; the surfaces name every folder `files`. A case-only rename of an Engram file (`<ID>.md`) blocks rewrites of that item until it is renamed back: the renamed file names another id, and a write refuses a name that differs only in case (RV3-4).
- Files adapter, MEMORY.md (RV-ADP-3): Engram items are never indexed in MEMORY.md, and the adapter never reads or changes the file. Claude Code loads the first 200 lines (or 25 KB) of MEMORY.md into every session by itself, outside the plane's read filter, and a retirement, ttl expiry or eviction never removed an item's line. The item files stay in the same folder, not a subfolder: Claude Code loads no other file of the folder at startup and reads topic files on demand with its file tools (https://code.claude.com/docs/en/memory.md, "How it works", read 2026-11-19), which the no-bypass hook blocks inside the folder (ADR 0014), and a subfolder would be reached by the same tools under the same root while changing every key. The cost: without the hook, Claude Code can open an Engram file with its Read tool as it can any file, and the model may write its own index line naming one. The round 2 amendment's "all or nothing" for the index and the review fix pass's index-line format lapse with the index.
- Delete refusals (RV-ADP-5): every permanent refusal is a `NotDeletableError`. Files adapter: `UnsafeKeyError` (a key that is not a memory file name, a file that is not a regular file with one name), `UnreadableItemError` (frontmatter that does not parse, a file that does not hold a valid item, an Engram file named for another id) and `ReadOnlyItemError`. Letta adapter: `UnsafeLettaPathError` and `NotMemfsRepositoryError`; `RepositoryBusyError` stays transient.
- Refs after a delete (RV-ADP-9): a ref names the store's record, not the item. After a delete, a rewrite of the same item id may land under a new ref: Mem0 gives the rewrite a new memory id, while the files and Letta adapters reuse `<id>.md`. The plane keeps the ref the latest write returned; a ref from before the delete may read nothing.
- Files adapter, temporary files (RV-ADP-10): the first write or delete of an instance, holding the folder lock, removes the `.<key>.<pid>.<n>.engram-tmp` files a crashed writer left, since every writer holds the lock while its own exists. The Mem0 adapter's header no longer says Mem0 links entities for every memory: with `infer: false` an add links none, and only an update that changes a memory's text links its entities (mem0ai 3.3.1).

Amendments made by card RV4, 2026-11-20 (branch `rv4`; proposed, for the lead's acceptance):

- Files adapter, a moved folder (backlog row "Adoption after a folder move"): fixed in core, with no store-specific branch and no new adapter capability. The reviewer proposed retiring a holder whose id is the same file's imported id under an older folder identity; core cannot compute a files adapter's ids, so the rule is the store's own listing instead: a projected item of the same store and scope at the ref the store now lists another id under, which the listing no longer holds, is retired in the transaction that adopts the record now there (ADR 0007's amendment of card RV4). Erased content stays refused across the move (ADR 0010's amendment of card RV4), and an item retired by its owner, a ttl or an eviction is not brought back under its new id while it holds the same content (`engram/adopt/rekeyed`). Two folders under one adapter name in one log still need two adapter names: the second folder's files are in another person scope, so their refs fail closed, as before. Two copies of one folder adopted in turn into the same scope under one adapter name do not fail closed, they churn: each adoption finds the other copy's ids at its refs, retires them and adopts its own, so every file costs one retire and one write event per adoption (review fix pass of PR #58, I-6, probe P3). Two adapter names are the remedy here too.
- Files adapter, Engram metadata written by hand (RV-ADP-4): a file under the name of its own new id, with Engram metadata and grants, is still read by the adapter, but adoption drops every grant the plane never recorded for that id (ADR 0034's amendment of card RV4), so the forgery the RV3 amendment names no longer reaches a grantee.

Amendments made by card A5 of the absorb plan, 2026-11-21 (branch `a5-conformance-cases`). Status: proposed. Deciders: drafted by card A5 of the absorb plan; for the lead's acceptance.

- Mem0 version 3 (the Context's "extract and update with ADD, UPDATE, DELETE, NOOP; history endpoint; graph variant" describes version 2). Mem0's guide "Open Source: Migrating to the New Memory Algorithm" (https://docs.mem0.ai/migration/oss-v2-to-v3, read 2026-11-21) says graph memory "is removed from OSS" and is now a Mem0 Platform feature, `enableGraph` and `graphStore` are removed, and search results no longer carry `relations`. It says extraction is "Single-pass ADD-only (one LLM call, no UPDATE/DELETE)": `add()` returns `ADD` only, and a changed fact "is stored alongside the old one" rather than replacing it. The installed `mem0ai` 3.3.1 (`dist/oss/index.d.ts` and `index.mjs`) matches: `MemoryConfig` has no graph field; `add()` with `infer: false` creates one memory per message and returns `{ event: "ADD" }`; the inferring path writes `ADD` history rows only. `update(memoryId, { text, metadata, expirationDate })`, `delete(memoryId)`, `deleteAll` and `history(memoryId)` remain as explicit methods, and UPDATE and DELETE now arise only from them: `update` appends an `UPDATE` history row and relinks entities when the text changed, `delete` appends a `DELETE` row. The `{collection}_entities` store feeds hybrid search's entity boost; the guide calls it unrelated to graph memory. Version 3 also has a read-time expiry filter: `expirationDate` on `add` and `update`, and `search` and `getAll` drop an expired memory unless `showExpired` is set, judged on the UTC date of the wall clock. Consequences for Engram: none in code. The adapter already adds with `infer: false`, rewrites through `update`, never sets `expirationDate` (so the filter never hides an item from the plane, which judges validity itself), and keeps `native_graph: false` and `native_history: false` (the history rows hold text, not the item).
- Capability honesty (card A5). A capability flag is now held to what it promises by the conformance suite's group "capability honesty", which runs a case only on an adapter that claims the flag: a store claiming `native_validity` stores a rewrite that only closes or reopens the validity window, hides nothing from `list` or `search` for being outside its window (the plane judges validity at the reader's time, as it judges status, ADR 0005 and its RV5 amendment, `valid_at`; Mem0's expiry filter above would fail this only if an adapter mapped `valid_to` to `expirationDate`, which this adapter never does), derives no window field from its own bookkeeping (`derivedFields`; the files adapter's modification-time `valid_from` would fail it), and with `history` keeps each version's own window, oldest first. These are necessary conditions, not a proof that the store does validity natively: the contract has no as-of argument (the plane judges validity itself, ADR 0005), and every current adapter, which stores the whole item, would pass them on items that carry Engram metadata, as the fake does with the flag forced on (`packages/adapters/test/conformance/meta.test.ts`); the files adapter would fail on a file without Engram metadata, whose `valid_from` it derives from the modification time. `native_graph` is refused outright while the contract has no method to show a graph; a graph store needs a contract amendment first. A test double in the test tree (`packages/adapters/test/conformance/validity.ts`) claims `native_validity` and passes, and the meta-test pins seven new broken adapters to the cases they must fail.

## Alternatives considered

No alternatives were recorded beyond the recommendation.

## Consequences

Unblocks A1 to A4. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.

Amendment of 2026-11-21, recording answers given on 2026-11-20 under the lead's delegation (`docs/tasks/lead-decisions.md`), carried by the answers card; the lead may overturn any:

- Item 41: memory search means one thing on every store. A hit is an item holding any query term, and core ranks the hits (`rankForRead`, as the shared retrieval of ADR 0009's amendment does); no adapter's own search decides what a read returns. Today the files and Letta adapters keep an item only when every term is in its content and the Mem0 adapter ranks by embedding similarity (finding RV-ADP-6), so the adapters and the conformance suite change in a card of their own (backlog). The registered conditions are unaffected, since none uses a store's search (ADR 0031, decision 2).

Amendment of 2026-11-22, branch `fix-letta-race-flake` (the M-2 flake). Status: proposed. Deciders: drafted by the flake fix's agent; for the lead's acceptance.

- Lock wait (round 2's "waits up to `lockWaitMs` (default 10 s) and refuses"): the wait now bounds one holder, not the whole queue. A waiter refuses, naming the holder, once one holder has kept the lock for `lockWaitMs`; each time the lock passes to another holder the wait starts again (`packages/adapters/src/lock.ts`, shared by the files and Letta adapters). The lock is not fair: a writer with another write queued in its instance takes the lock again before any waiter polls, so four Letta instances writing five items each ran in four blocks of five, and the last waiter sat through fifteen holds; on a loaded machine that passed 10 s while every holder was making progress, and a write was refused (`packages/adapters/test/letta/repository.test.ts`, M-2). The cost: a waiter behind an unending stream of other writers now waits as long as the stream lasts instead of refusing after 10 s; a stuck or slow holder is still refused after `lockWaitMs`, and a dead one is still broken at once.
