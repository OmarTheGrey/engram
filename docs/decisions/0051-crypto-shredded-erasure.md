# ADR 0051: Crypto-shredded erasure: a data key per person scope, wrapped under an operator key behind an injected provider; shredding adds to redaction and replaces nothing

Status: accepted, 2026-11-29, under the lead's delegation of 2026-11-28 (`docs/tasks/lead-decisions.md`, "The lead's answers, 2026-11-28": new ADRs as needed, none contradicting the set); the lead may overturn it
Deciders: the orchestrating session, under the lead's delegation of 2026-11-28; drafted by card E9.11 of the second absorb plan
Supersedes: nothing. It builds on ADR 0010 (erasure, with every amendment through card E1.7's of 2026-11-28), ADR 0038 (the chain, with card E1.9's chain version 2), ADR 0021 (person and role scopes), ADR 0024 (one migration list for both backends) and card E2.14's policy option `erasure.mode`. It amends none of them.

## Context

- **What erasure reaches today.** Offboarding (ADR 0010, card E9.7 and its amendments) deletes a person scope's items from the store, removes them from the projection and redacts their content in every earlier event. Its deletion report names what it cannot reach: a store's own history (`native_history`, such as Letta's git), pi session files that mirrored the events, and backups. A copy of the log file taken before the offboarding keeps the content too, as do SQLite's free pages and write-ahead log and Postgres's dead tuples until they are reused.
- **Crypto-shredding.** The practitioner pattern (`docs/readings/litreview/methods-crypto-shredding.md`) encrypts a subject's data under a key of its own and erases by destroying the key: every copy of the ciphertext, wherever it went, stops opening. Compartment (`MaxFreedomPollard/Compartment`, `src/compartment/crypto.py` and `wire.py` at `98d4917181c04e5efa41e82ba455b25084edc99f`, Apache-2.0, licence read at that commit) does this for an offline vault: a random data key per record, wrapped under the vault's master key with the record id as associated data, destruction of the wrapped key as the erasure, and caps on the key-derivation parameters a header may ask for.
- **The research's place for it.** The first absorb plan named it the first thing after the thirty; the second plan splits it into this card (the decision and the key table), E9.13 (sealing content and shredding in offboarding) and E9.14 (the signed receipt).
- **Constraints.** No change to `schema.ts` and no `schema_version` bump (AGENTS.md rule 5; a bump moves H1's cassette keys). Core reads no clock, draws no randomness and does no key I/O. Both Db backends. Off by default and in every registered preset, since the H1 runs start on 1 December.
- **What it must not contradict.** ADR 0010's redaction and its kept hashes (the amendment of 2026-11-21, item 38 option (a), "decision 38a" in the plan: erase events keep merging content hashes of records left in or not found in a store, so adoption refuses the erased content again); ADR 0038's skeleton, salted commitments, salt deletion and chained manifest; card E1.9's attestation digests in the chain.

## Decision

1. **One data key per person scope.** A person scope (`person:<id>`) holds at most one live data key: 256 random bits, with a version, made on first use. Role, team and org scopes never hold one: their content is the organisation's and outlives a person (ADR 0010's answer to item 38: erasure does not reach a promotion out of the person scope). Per-record keys, as Compartment has, buy nothing here, since the plane erases a person at a time.
2. **Where keys live.** Only wrapped, in a side table of the plane's own log database, `data_keys`, created by migration 7 in `packages/core/src/db/migrate.ts` on SQLite and Postgres: scope, version, the id of the operator key that wrapped it, the wrap algorithm, the wrapped bytes, when it was made and when it was shredded. Never the key itself. The table is not a projection, and `rebuild()` leaves it alone.
3. **The operator key is behind an injected provider.** The wrapping key (the operator key, a key-encryption key) is held by a `KeyProvider` passed in at the boundary (`packages/core/src/crypto/keys.ts`), as ADR 0038's checkpoint signer is: it draws each new data key's random bytes, wraps it and unwraps it with authenticated encryption, and core sees only the operator key's id. Core checks what it is given (a 32-byte key, a wrapped form longer than the key that opens again under the provider to the same key, a row whose recorded algorithm is the provider's) and passes every time in, as core's ISO 8601 UTC timestamps. A nonce-based wrap (AES-256-GCM, which `node:crypto` offers; it offers no AES-GCM-SIV, and its AES-KW binds no associated data) draws a fresh random 96-bit nonce for every wrap and stores it with the wrapped bytes: one nonce reused under one operator key leaks the XOR of the two data keys and lets wraps be forged. A misuse-resistant wrap needs none. Core cannot check this, so the provider's own tests must (two wraps of one key differ; the test provider's are). The associated data of a wrap is a tag, the scope and the version (`engram.data-key.v1`, NUL-separated), so a wrapped key moved to another scope or version, or edited, does not open. Where a provider derives the operator key from a passphrase, its key-derivation parameters are its own constants, never read from the table or from any file an attacker could edit; a provider that does read them bounds them before deriving, as Compartment's `KDF_MAX_*` caps do. The table holds no derivation parameters.
4. **How content is sealed (built by card E9.13).** Under `erasure.mode: shred`, an item's `content` in a person scope is sealed under its scope's live data key with authenticated encryption, the item's id as associated data (Compartment's record id), wherever Engram writes it: the event bodies that carry the item, the projection row, the explanation rows, and a store written through an Engram wrapper (the files adapter's, per E9.13's card). The sealed form is a string with a version prefix, so no item or event changes shape. The write gate, the content guards (ADR 0039) and the lints see the plaintext before it is sealed; every reader of content in core goes through one unseal, after the read matrix admitted the reader. The merging content hashes and the provenance hashes are computed from the plaintext, as now. The evidence part of a lint event's reason about an item in a person scope (the part ADR 0038 already commits; a model lint quotes the item's text there, card L9) is sealed the same way, under the item's scope key, so it is not left as a plaintext copy of the content. A promotion or a handover out of a person scope unseals the content and writes plaintext into the target scope, so no content outside a person scope is sealed under a person key and shredding never reaches a promoted version (ADR 0010, item 38, answer (c)). E9.13 fixes the envelope's bytes and tests both rules.
5. **Shredding adds to redaction, and replaces nothing.** Offboarding under `shred` does all that ADR 0010 and its amendments say, unchanged: the mark, the store deletions and sweep, the projection removal, the redaction of every earlier event, ADR 0038's salt deletion and chained manifest, the report. In the transaction that appends the report it also shreds the scope's data keys (`shredDataKeys`): their wrapped bytes are deleted and each row stays as a tombstone with its version, operator key id and times, holding nothing about content. The report's reason names the versions shredded. A crash before the report leaves the key and the frozen scope, and the rerun completes both. A shredded scope is not given a new key (`ensureDataKey` refuses), in line with item 38's answer (a): an offboarded person scope stays empty until the person is added again, which a later card builds, as the scope's key version n+1. So under `shred` a write into a shredded scope is refused with a reason (E9.13), which builds answer (a) in that mode only; under `redact` today's acceptance of such a write stands, as ADR 0010 records it (not built). What shredding adds is reach: every copy of sealed content that the redaction could not rewrite (a store's native history of a sealed record, pi session files mirroring sealed events, an export, a database page or write-ahead log, a backup once the operator key is rotated) stops opening.
6. **Redaction stays the default, and the log is still rewritten under shred.** `erasure.mode` absent means `redact`, which is today's behaviour, and no preset or registered config sets `shred`. Dropping the log rewrite under `shred`, so that the log becomes strictly append-only, would change ADR 0038's verifier rule (an erased event is one with no salts, a manifest entry and the redaction marker) and the one rewrite of the append-only log, which ADR 0010 allows against ADR 0003; it is a later ADR's question, once shredding has been measured.
7. **What the chain and the attestations keep.** Nothing in ADR 0038 or card E1.9 changes. Under `shred` the committed value of `item.content` is its sealed string; the redaction replaces it with the marker and deletes the event's salts as now, so the chain verifies across a shredded offboarding exactly as across a redacting one. Attestation digests (chain version 2) cover identifiers only and are untouched. The `data_keys` table is outside the chain: an edited row fails to unwrap (the associated data and the authentication tag), and a row deleted without a report that shredded it is a key missing with no record of why, which E9.13's check reports. Neither proves the content was read.
8. **Decision 38a's hashes are not shredded.** The merging content hashes the erase and sweep events keep, for records left in or not found in a store, are computed from the plaintext and stay in the log after the key is gone. Their purpose is to recognise erased content when it comes back, which they must do without the key. ADR 0010's caveat stands: for short, guessable content a hash can be confirmed by guessing. A sealed record whose key was shredded cannot be opened, so adoption treats it as erased content (E9.13).
9. **Backups and residue are reached by rotating the operator key.** A copy of `data_keys` taken before a shred (a backup of the log, a free page, a write-ahead log, a dead tuple) still holds the wrapped key, and opens with the operator key that wrapped it. So the erasure of such copies is complete only when the operator, after the shred, rewraps every live data key under a new operator key (`rewrapDataKeys`, which refuses the same operator key id and checks every new wrap opens before it commits) and destroys the old one. Destroying it makes every pre-rotation backup's sealed content unopenable for everyone, not only for the shredded person: a restore from such a backup loses every sealed scope, so the operator takes a fresh backup after each rotation. Defence in depth, never the guarantee, for E9.13: SQLite's `PRAGMA secure_delete = ON` (freed space inside a live page is otherwise kept) and `PRAGMA wal_checkpoint(TRUNCATE)` after a shred; on Postgres, `VACUUM` marks old tuples reusable but does not zero them, and archived write-ahead log is a backup. Until then the deletion report under `shred` (card E9.13) says that a backup together with the old operator key reopens the content. How often to rotate is the operator's, as is the operator key's custody.
10. **Off until built.** The option row `erasure.mode` stays in `NOT_BUILT_YET` (`packages/core/src/policy/options.ts`), so the loader, `Plane.simulate` and the Cedar export refuse `shred` until card E9.13 builds it and decides whether the Cedar export carries it (ADR 0041); it is not an authorisation decision, so refusing it there with a reason is the expected answer. This card builds the table and the provider, and nothing calls them yet.

## What is not protected

- Content Engram does not write sealed: what Mem0 and Letta keep of their own (Mem0's extracted facts and embeddings, Letta's memory blocks written by Letta), a Claude Code memory file the person wrote, and any store reached without an Engram wrapper. The guarantee is stated per store.
- Content outside the plane: the agent's own conversation in pi session files and in a model provider's logs, a person's own copies, derived data such as embeddings, and promotions out of the person scope (ADR 0010, item 38).
- Anyone who holds the operator key and a copy of `data_keys` from before the shred, until the operator rotates; and a running plane process, which sees plaintext.
- What stays plaintext in any copy taken before the redaction (a backup, the write-ahead log, a free page, a dead tuple), which shredding does not reach and only ADR 0010's redaction rewrites in the live log: an item's `provenance.ref`, `provenance.session_entry_id` and `provenance.hash`, the merging content hashes, and, until E9.13 seals it, the evidence part of a lint reason, which may quote the item's text. The salted commitments of ADR 0038 cover these parts in the chain, but the copies hold the values themselves.
- What ciphertext reveals by itself: its length, and that an item existed (ids, times, decisions and the reasons of non-lint events stay in the log by ADR 0010).
- Whether key destruction satisfies GDPR Article 17: the sources are practitioner posts, and it needs legal review (the reading's risk).

## Alternatives considered

- **Keys derived from one master key and the scope's id** (HKDF). No table, and no way to erase one person without destroying everyone's key or keeping a deny-list.
- **A key per record or per event** (Compartment's unit). Finer, and every key is one more row to manage, for no erasure the plane needs.
- **A key service** (a cloud KMS). Stronger custody, and a network and a vendor. The interface is synchronous (ADR 0024) and is called inside the log's transaction, so a provider over one fits only if it presents a local, synchronous wrap, for instance by holding an unwrapped operator key, and never holds the log's lock across a network call.
- **Shredding instead of redaction.** Makes the log strictly append-only, and changes ADR 0038's verifier and the one rewrite ADR 0010 allows against ADR 0003; left to a later ADR (decision 6).
- **Keys in the event log.** Would put key material under the chain and the export; a side table keeps it apart and deletable.

## Consequences

- Card E9.13 seals content and shreds in offboarding, lifts the option row, and measures the residue before and after (card X19's check). Card E9.14's receipt can name the key versions shredded.
- A person scope's first write under `shred` costs one key draw and one wrap; later reads cost one unwrap per handle.
- The CLI's provider (E9.13) reads the operator key from a place the operator holds; losing it loses every sealed scope, which the documentation says.
- Destroying an old operator key after a rotation makes pre-rotation backups unrestorable for sealed content, for every person; a fresh backup follows each rotation.
- No registered result moves: nothing calls the table or the provider until E9.13, and no preset sets `shred`.
