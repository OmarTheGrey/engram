# ADR 0010: Retention never deletes; eviction retires; long-horizon arm is mandatory

Status: accepted, 2026-11-02
Deciders: Omar (lead)
Supersedes: the proposal of the same number in `docs/decisions/README.md`

## Context

Ground Truth First's tenure crossover (budgeted memories win at three weeks and lose at nine because eviction removed old material); MemSecBench's finding that selective repair damages benign memory.

## Decision

Retention budgets per scope trigger `retire` events, never deletes; retired items stay replayable and can be reinstated by event. Hard deletion exists only for person-scope erasure and emits a deletion report. The evaluation includes a long-horizon arm so the cost of eviction appears.

Amendments made when implementing card E2.4, 2026-10-29:

- The mechanism is ADR 0025 (`docs/decisions/0025-retention-semantics.md`): expiry retires with op `retire`, budget overage with op `evict` in the rule's order (recency, utility, manual), both decided by the pure `evaluateRetention` (packages/core/src/policy/retention.ts) and appended by `Plane.retain` and the write path's budget check (packages/core/src/plane/retention.ts). "Never deletes" holds in both places it could fail: the event sets the projected status to retired, and the plane never writes or deletes the item in the store, so the store keeps the bytes and adoption leaves an item retired by retention retired while the store has it unchanged (ADR 0007's adoption amendment).

Amendments made by card E9.7, 2026-11-06 (branch `e9-7-offboarding`):

- The person-scope erasure is implemented by `offboard` (packages/core/src/plane/offboard.ts). Every item in the person scope, every version and status, is deleted from the store, its projection and explanation rows are removed, and its content, provenance ref and evidence hash are redacted in every earlier event that carries it; one `retire` event per item under `engram/offboard/erase` (events.ts `ERASURE_ID`) then removes it from the projection and from replay (`itemsAt`), so a rebuilt projection equals the incremental one and the item never comes back from the log (`packages/core/test/replay/erasure.test.ts`). The redaction is the one rewrite of the append-only log (ADR 0003): without it the log would keep what erasure deletes. The events, their ids, decisions and reasons stay, so what was decided remains auditable.
- The deletion report names what was erased and handed over by id, the store refs deleted and any the store failed to delete, and what the call cannot reach: a store's own history (`native_history`, such as Letta's git), pi session files that mirrored the events, and backups. It carries no content. One summary event (`engram/offboard/report`) records the offboarding.

Amendments made in the review of PR #33, 2026-11-13, accepted by the lead on 2026-11-19:

- Erasure deletes a store ref only when no item outside the person scope holds it. A ref shared with such an item (a version of the same store record, as adoption makes) is kept in the store, since deleting it would delete that item's bytes; the erased items' copies in the log are redacted all the same, and the deletion report names how many refs were kept (`packages/core/test/unit/plane/offboard-edges.test.ts`).

Amendments made by the post-merge integration fixes, 2026-11-13 (the review of the twelve PRs merged that day), accepted by the lead on 2026-11-19:

- A store's delete failure is either transient or permanent. A permanent refusal is a `NotDeletableError` (packages/core/src/adapter.ts, part of the Adapter contract; the files adapter's `ReadOnlyItemError` for a memory file Engram did not write is one), so core tells the two apart with no store-specific branch.
- On a transient failure the item is not erased in that run: it stays in the store, the projection and the log, unredacted, with one deny event (`op` retire, `engram/write/store-failure`, the reason naming the error and `engram/offboard/erase`), and the deletion report lists it under `store_failures` with its ref and items. Offboarding again once the store recovers erases it. Erasing it from the log while its bytes stayed in the store let adoption bring it back with nothing recording why.
- On a permanent refusal no rerun would succeed, so the item is erased from the projection and the log as any other, and the report lists its ref under `left_in_store` for the person to delete in the store. Its erase event names the merging content hashes (case, width and invisible characters folded, the form `packages/core/src/content-hash.ts` gives a blocking rule) of every erased version and of the record the store still holds, and adoption refuses that item's own record, under its id, while it holds one of them, with one deny event (`engram/adopt/erased`, naming no content), decided in the write queue so an adoption queued behind the offboarding sees the erase events. Edited content, a file the person rewrites after erasure, and another person's own file with the same name adopt normally: the files adapter derives an imported id from the file name, so refusing by id alone would hide them, and a hash matched against every erased item would refuse another person's file that only shares the text (rechecks of PR #41). Those hashes are the one trace of erased content the log keeps, and only for records still in a store; for short, guessable content a hash can be confirmed by guessing, which the deletion report says (`packages/adapters/test/plane/offboard-files.test.ts`, over the Claude Code memory fixture).
- Each erase event's reason says what happened to its item in the store: deleted, left in the store that refuses the plane's delete, kept because an item outside the person scope holds the same ref, or no store record.
- The redaction reaches lint events (card L1), which carry an item by id only and their evidence in `reason`. A lint event is redacted when it is about an erased item (its `item_id`), or when its reason names an erased id, or holds a content or evidence hash of an erased version that no surviving item also holds (as its content hash or its provenance hash). An erased item's evidence hash of a source that survives is never matched. A hash a survivor holds stays readable in that survivor, so redacting by it protected nothing and erased findings about surviving items (review of PR #41). A redacted lint event keeps its lint id, severity and rule, and its reason becomes `<lint_id> (<severity>): [erased]`. A lint event changes no item, so replay and a rebuilt projection are unchanged (`packages/core/test/unit/plane/offboard-edges.test.ts`, on SQLite and embedded Postgres).

Amendments made by card E2.6, 2026-11-19 (branch `e2-6`; proposed, for the lead's acceptance):

- Offboarding marks its erasure before deleting any store record (one `engram/offboard/begin` event, closed by the report event), and until the report closes it nothing in the person scope may change (`engram/offboard/erasing`); a writer on another handle whose decision preceded the mark deletes what it wrote (ADR 0007's amendment of the same date). The erasure commits what the mark read that the projection still holds. A crash between the mark and the report leaves the person scope frozen until offboarding runs again.
- An erased id is never written or adopted again (`engram/write/erased`, `engram/adopt/erased`), except a record the erasure left in a store that refuses the plane's delete, which adoption takes again once its content changes, as before.
- Review fix pass of PR #50, as its verification left it (V-1, V-5): the offboarding itself, before its report, deletes from its person scope's store every record no projected item holds under an id the log never allowed or an erased id whose record it deleted (`engram/offboard/swept`), and adoption refuses and deletes a record under an erased or swept id that reappears later. A record that appears after the report under an id the log never recorded is the person's again: the plane accepts a write into an offboarded person scope, and adoption accepts that record alike. Whether a completed offboarding should instead refuse every later write into the person scope is a policy question for the lead (open question below). A report closes every mark open when its own mark was appended, so a rerun after a stopped offboarding completes it.

- Verification pass 3 of PR #50 (V3-1, V3-2, V3-7, V3-8), correcting the bullet above. The report does not end the hard deletion: a writer that crashes between its store write and its commit can still land erased content after it. Erased content is therefore also traced by lineage: a first write, or a store record in any scope, whose lineage names an erased or swept id is refused, and adoption deletes such a record; the sweep lists every scope the log names for such records, not only the person scope. Each sweep deletion is checked under the log's lock afterwards, so a write another handle committed meanwhile is written back instead of swept. A record the sweep could not delete because the store refuses for good is refused while it holds that content, and adopted again once the person edits it, as an erasure's left-in-store record is. What the deletion reaches is: the person scope's items and their store records, every store record left under an erased, swept or never-committed id in the person scope, and every store record anywhere whose lineage names an erased or swept id, each once an adoption of its scope has run.
- Verification pass 4 of PR #50 (V4-1, V4-2). A first write's lineage is checked again under the log's lock at its commit, as is a promotion's new version's, so a derived write decided before the mark and committed after the erasure is refused (`engram/write/erased`) and its record deleted by its writer. One gap is left: a promotion or derived write into a team or role scope that crashes after its bytes land and after the sweep stays in that scope's store until an adoption of that scope or a later offboarding's sweep deletes it. The plane adopts only the person scope through `engram read`, and no surface adopts a team or role scope, so in the dogfood such bytes can stay dormant in the store (never projected, never read through the plane) indefinitely. A backlog row tracks covering it.

Amendments made by card RV4, 2026-11-20 (branch `rv4`; proposed, for the lead's acceptance):

- A record holding content an offboarding erased from a scope and left in a store that refuses the plane's delete is refused in that scope under any id the projection does not hold (`engram/adopt/erased`, `erasedScopeContent` in `packages/core/src/events.ts`), not only under the erased item's own id. A store may give the record it kept a new id: a moved files folder gives each Claude Code file a new imported id, and before this card the erased text was adopted again under it. The hashes are the ones the erase and sweep events already carry; nothing new about erased content is kept. Another person's file with the same text, in another scope, still adopts. An erased file stays refused across the move until it changes (`packages/adapters/test/plane/rv4-files.test.ts`).
- Review fix pass of PR #58 (I-1), correcting the bullet above, which held only when the erasure ran against the folder as it then stood. The adapter contract makes deleting an unknown ref a success, so an offboarding run against a folder's old root after the folder moved recorded every item as deleted, kept no hash, and the next adoption of the new root brought all of it back into the person scope. Now the erasure reads each ref before deleting it, and a ref the store holds no record at is not proven deleted: the item is erased all the same, the report lists the ref under `not_found_in_store`, and its erase event carries the erased versions' merging hashes under `LEFT_CONTENT_CLAUSE`, with `NOT_FOUND_CLAUSE` beside it. What holds: such content is refused in the person scope under any id while a record holds it (case, width and invisible characters aside); a record under the erased id itself is refused while it holds that content and adopted once it changes, as a left-in-store record is (review fix pass 2, N-3: before it, a folder moved back with a new file under an erased id was refused forever); a record whose content changed under a new id adopts as new content. The log keeps those hashes for records that may still exist, as for records left in a store. The adapter contract is unchanged: core tells absent from deleted by the adapter's `read`, so no adapter changed and no conformance test was needed (`packages/adapters/test/plane/rv4-review.test.ts`). The scope-wide check reads only erase and sweep events, once per adoption (I-7).

Amendments made by card E1.7, 2026-11-28 (branch `a2-e1-7`; proposed, for the lead's acceptance). They close the two gaps the Quint model found (card E1.5, `specs/README.md`) and three differences the trace replay found (card E1.8, E18-F1, E18-F2, E18-F4):

- A swept id is never written again, as an erased id is not: a new item under an id an offboarding's sweep took out of the store is refused (`engram/write/erased`), at the decision and again at the commit. Adoption already refused and deleted a record under such an id, so a write committed under it lost its record to that purge.
- The sweep's put-back writes back the projected item only while it lives at that ref and its scope is not being erased; otherwise it deletes the record, as a stale writer's settle does, so a third offboarding that erases the item between the put-back's read and its write no longer leaves erased content in the store.
- Each purge of a refused record checks under the log's lock, just before its delete, that the record's item has not changed, nor an erasure of its scope begun, since the refusal (for a purge an earlier adoption decided, since the listing), and otherwise leaves the record to the next adoption.
- While a person scope is being erased, adoption retracts nothing in it: the erasure takes the item out. A record refused only because its scope was being erased (`engram/offboard/erasing`) is gated again once that erasure has completed; the refusal was for the time being.

## Open questions for the lead

Answered on 2026-11-20 under the lead's delegation (`docs/tasks/lead-decisions.md`, item 38); the answers are in the amendment of 2026-11-21 at the end of this ADR.

- Should a person scope that a completed offboarding erased refuse every later write and adoption, so the scope stays empty unless the person is re-added? Card E2.6 treats a later write and a later record alike and accepts both.
- Content the person wrote before the offboarding under a fresh id with no lineage to the erased items (a write decided before the mark whose writer crashed after its bytes landed and after the sweep, or a copy the person made by hand) is not recognisable as erased content and is adopted as the person's. Should the plane keep content hashes of every erased version, beyond the left-in-store records ADR 0010 already allows, to refuse such copies? That trades a hash of erased content in the log against content that comes back.
- A Claude Code memory file the plane cannot delete (`NotDeletableError`) is refused while it holds the erased content, and adopted again, under the erased id and with the erased text, once its content changes in any way. Claude Code appends to these files routinely, so one appended line brings the erased text back into the projection (verification finding V4-6 of PR #50). Card E2.6 keeps the rule as ADR 0010's amendment of 2026-11-13 set it. Should an edited left-in-store record instead be adopted only under a fresh id, or only with the erased lines removed?
- A committed promotion of a person item into a team or role scope, made before the offboarding, carries the erased item's content under a fresh id with lineage to it, and stays: it is the scope's, not the person's. Should erasure reach such versions?

## Alternatives considered

No alternatives were recorded beyond the recommendation.

## Consequences

Unblocks E2.5, X9, Twin erasure. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.
