# ADR 0026: Promotion: confirmations are independent corroboration, reviewers are user-sourced members, a promotion is a write under the target's rule

Status: accepted, 2026-11-02
Deciders: Omar (lead)
Supersedes: nothing; it gives ADR 0011 (one lifecycle, replay admission) its promotion mechanism.

## Context

The policy says episodic items become semantic "after k confirmations or review" and procedural candidates become active "after replay validation" (ADR 0011), and `Plane.promote(actor, itemId, toScope, at)` is declared, but nothing defines a confirmation, a reviewer, or how a promoted item is versioned. Two results constrain the design. Origin-Bound Authority (2606.24322) proves that any gate judging content or lineage is launderable, and names planted corroboration as one of the three laundering channels: an agent writing the same fact k times must not promote it; elevation is sound only through independent trusted principals. Authorization Laundering (2609.01836) shows an agent writing permissions into its own memory grants itself authority executors act on 98.6 percent of the time; an approval is an authorisation and must come from a user. Generative Agents (2304.03442) and Eywa (2605.30771) model consolidation as higher-level items that cite their evidence. MSCE (2607.16621) and SKILL.nb (2606.08049) activate skills on reliability scores and Wilson bounds; Engram's k of n is more conservative and has to say so.

## Decision

1. **A pure evaluator.** `evaluatePromotion(policy, actor, item, target, evidence)` in `packages/core/src/policy/promotion.ts`, with `evidence = { confirmations, review, validation? }`, decides with a reason and a policy id: `<policy>/promotion/episodic-to-semantic`, `<policy>/promotion/review`, `<policy>/promotion/procedural`, `engram/promote/membership`, `engram/promote/not-candidate`, `engram/promote/no-evidence`, `engram/promote/reviewer`.
2. **Confirmations** are counted from the log, never stored: allowed writes in the same scope of items whose normalised content hash equals the episodic item's (ADR 0018's exact rule), each by a different actor, with provenance kind `user`, `document` or `tool`. Writes with kind `model` or `compaction` never count (derived content cannot elevate, 2606.24322); the item's own write counts once. Promotion to semantic is allowed when the count reaches `promotion.episodic_to_semantic.confirmations`.
3. **Review.** When `or_review` holds, a reviewer may promote below k. A reviewer is a member of the target scope who is not the item's owner and whose actor source is `user` (set by the harness; a `model`-sourced actor cannot approve). The promote event's actor is the approver. A scope whose write rule has `requires_review` admits writes as `candidate`; promoting such a candidate to active is the same review path, so "review path records approver" holds for both.
4. **Procedural admission.** A procedural candidate becomes active only with a validation record `{ k, n }` where `k >= replay_k` and `n >= replay_n`; without one the promotion is denied (`engram/promote/no-evidence`). Card D3 supplies the record from replay. The preset comment states the one-sided Wilson upper bound on failure the chosen k of n implies, so the number is argued over, not assumed.
5. **A promotion is a write under the target's rule.** Widening scope or changing class is evaluated as a write of the promoted item into the target scope (membership, sources, classes, floor, review of decision D4 and ADR 0007), so a promotion never lands where a write could not; invariant 2's oracle covers promotions.
6. **Versioning.** A status-only transition (candidate to active) is in place: same id, version plus one, one `promote` event carrying the item. A class or scope change is a new id whose `lineage` names the source item and every confirming item (the evidence pointers of a reflection); the promoted item's provenance kind is the least trusted among its sources, its actor the approver or the promoting actor; the source is retired by a `retire` event (`<policy>/promotion/superseded`) in the same queue slot (ADR 0005, decision D1). A `derived_from` field on provenance (the trust ceiling the literature review asks for) is a schema change and waits for its own PR; lineage carries the pointers until then.
7. **Ask.** When `requires_review` holds and the actor is not a reviewer, the result is decision `ask` with a null item and one `gate` event, so the request is visible in the review queue (E8.8) without landing.

Amendments made when implementing card E2.5, 2026-10-29 (choices this ADR left open):

- `Plane.promote` takes an optional fifth argument `{ review?: boolean }`: an actor approves by asking to, and an ineligible actor asking is refused (`engram/promote/reviewer`). An eligible actor who does not ask is not treated as a reviewer, so a confirmation count is never silently replaced by an approval. The CLI's `--review` sets it.
- The validation record is not a Plane argument: a caller-supplied `{ k, n }` would be a self-granted authority (2609.01836). The evaluator accepts one; the plane passes none until card D3 gives it a source, so no procedural candidate becomes active through the plane before D3.
- "k >= replay_k and n >= replay_n" alone would admit 4 passes in 100 runs under 4 of 5. The evaluator also requires the pass rate `k / n` to be at least `replay_k / replay_n` (and `k <= n`).
- A confirmation counts once per item (its first trusted write) and once per actor (the event's actor, which the plane sets to the harness's actor); the item's own write counts like any other. Confirming items in the lineage are one per counted actor other than the item itself, in log order.
- Trust order for "least trusted", most trusted first: user, document, import, tool, model, compaction (ADR 0025's re-admitting sources first, ADR 0004's compaction last).
- What is a candidate: not retired; the target is the item's own scope or one at a wider level (person, role, team, org), never a sibling or a narrower one; and something changes. An episodic item always becomes semantic (a new version, even in its own scope). A semantic candidate, or a widening of an active semantic or procedural item, needs a reviewer. A procedural candidate needs its validation record, which a review cannot replace.
- Missing evidence that a review could supply asks (`gate`, decision `ask`) when the target requires review, else denies with `engram/promote/no-evidence`. An unknown item id and an item outside the actor's scopes get the same `engram/promote/membership` refusal, with no scope named.
- A promotion is judged as a write by the promoting actor with the promoted item's provenance (the least trusted kind), not the actor's source. So model-written content never leaves person scope, even by promotion: source isolation (ADR 0007) holds for it, which narrows ADR 0004's "cannot be promoted beyond person scope without a gate pass" to "cannot leave person scope"; a person restates it as user content instead.
- A new version keeps the source's owner, content, confidence, validity, ttl and grants. A store failure after the gate allowed appends one `promote` deny event (`engram/write/store-failure`) and rethrows, as a write does. The target's budget check runs after a landing promotion, in its queue slot.

Amendments made in the review fix pass of card E2.5, 2026-10-29 (review P5, decisions taken by the orchestrating session). Where they differ from the list above, these replace it:

- P5-1: a reviewer is not the owner and not the actor of any allowed `write` or `update` event on the item or on any version its lineage reaches, whoever the item names as owner (`owner` is a field the writer sets). The plane gathers the authors from the log; invariant 2's generator writes items whose author is not their owner, and its oracle finds the authors in its own scan of the events.
- P5-2, a limit stated plainly: the CLI does not authenticate. `--as` and `--member` are taken as given and `engram promote` sets source `user`, so through the CLI the distinct-actor rule and the reviewer rule hold only as far as the single-user machine it runs on; a CLI promotion with `--review` is only as trustworthy as that machine. ADR 0006's "set by the harness, the caller cannot" holds for the pi extension, not for the CLI. `engram promote --help` says so. So that a model cannot use the CLI to do the same, `engram` is on the pi extension's store-command block list (packages/pi-extension/src/bash.ts), with a real-session test.
- P5-3: a promotion that changes scope needs a user-sourced promoter (`engram/promote/widening-source`); choosing where content is disclosed is an authority act (2609.01836). A promotion within the item's scope (an episodic item made semantic there, a candidate made active) keeps the rules above.
- P5-4: an item past its ttl (the read path's rule: the tighter of its own ttl and its retention rule's, `valid_from` plus ttl not after `at`) is not a candidate (`engram/promote/expired`). `evaluatePromotion` takes the target as `{ scope, at }`.
- P5-5: confirmations count only items whose status is active now, the item's own write aside. A promotion is denied (`engram/promote/duplicate`) when an active item of the promoted class in the target scope already holds the same content (strict form), so a fact is not promoted again through its confirmers.
- P5-6: the retired-content rule (ADR 0025) ignores a source retired as `<policy>/promotion/superseded`, whose content lives on in its new version, and any content an active item in the scope still holds.
- P5-7 and P5-11: the promoter must be able to read the item as `read` would reach it (a readable scope or a live grant naming it); otherwise the refusal is the opaque `engram/promote/membership` one an unknown id gets. Membership of the item's scope is no longer required, for reviewers or anyone. A promoter who cannot read the target scope gets the decision's event, the audit record, and a null item. A duplicate is named only to a promoter who can read the target.
- P5-10: for a new version, the ref check treats only the source and its own lineage as related, not the confirming items its lineage also names.
- P5-12: confirmations and the duplicate check compare content in a strict normal form (format characters dropped, whitespace collapsed; no NFKC, no case folding), so "US" never confirms "us" and "10²" never confirms "102": for corroboration, not merging is the safe direction. The retired-content rule keeps the merging form, where merging is the safe direction. Both are exported under names that say so (`strictContentHash`, `mergingContentHash`; ADR 0018's amendments).

Amendments made in the verification of the fix pass, 2026-10-29 (review findings P5-14 to P5-18, decisions taken by the orchestrating session). These supersede the P5-11 decision above and refine P5-7 and P5-12:

- P5-15, superseding P5-11: a read grant never lets anyone move or retire an item (ADR 0006, decision D4: grants let others read, never write). Reach (a readable scope or a live grant) only chooses between the opaque refusal and a named one. A promotion lands only when the promoter is also a member of the source's scope, or is the item's owner and the source is the owner's own person scope; otherwise it is refused under `engram/promote/membership` with a reason that names the rule. Invariant 2 puts live grants on its source items and its oracle requires source-scope membership itself.
- P5-14: content holding any default-ignorable code point, format character (Cf) or Unicode tag character (U+E0000 to U+E007F) is never promoted (`engram/promote/hidden-text`); the reason names how many such characters there are, never the characters. The strict form of confirmations now collapses whitespace only and keeps every other character, so a confirmation matches exactly what its writer wrote and a hidden payload never matches plain restatements. This refines P5-12, whose strict form dropped format characters. The oracle checks hidden text with its own code.
- P5-16: an actor of a write that counts as a confirmation (trusted source, item still active, same content in the strict form, in the item's scope) cannot also approve the promotion as its reviewer, the same rule as for authors.
- P5-17: invariant 2 generates confirmers retired before the promotion and a guard requires a refusal that only those retirements caused, so dropping the rule that only active items confirm fails the invariant.
- P5-18: the pi extension blocks the CLI's other routes as well as its name (ADR 0014's amendments, with the text check's remaining limit).


- Confirmations by distinct provenance `ref` or `session_entry_id` only: launderable by one agent across sessions (channel L-c of 2606.24322). Rejected.
- Any member of the target scope as reviewer, owner included: self-approval; rejected on 2609.01836.
- A smoothed reliability score instead of k of n for procedures (MSCE): the score belongs on the item (D4, a schema change) and lands with drift detection; k of n is the admission rule until then.
- Promotion in place for class changes: loses the episodic evidence as a separate version (A-MEM's lineage-free evolution, 2502.12110); rejected under ADR 0005.

## Consequences

Card E2.5's acceptance ("fixture promotes only after k; review path records approver") has a definition. `engram promote` lands with it. Invariant 2 gains promotions; a second reviewer and a `decision` entry go with that change. The preset values for `confirmations`, `replay_k` and `replay_n` stay proposed. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.
