# ADR 0002: Memory item schema, versioning and generated contracts

Status: accepted with amendments, 2026-11-02
Deciders: Omar (lead)
Supersedes: the proposal of the same number in `docs/decisions/README.md`

## Context

CoALA's three classes (episodic, semantic, procedural); Zep's bi-temporal edges; Eywa's evidence-before-belief; MemOS's MemCube, which we must compare to field by field; the roadmap rule that schema changes are one PR.

## Decision

(a). Zod 4 has native JSON Schema export with `io`, metadata and registries, and the extension already lives in TypeScript. Fields: `id` (UUIDv7), `class`, `scope`, `owner`, `content`, `provenance`, `confidence`, `valid_from`, `valid_to`, `ttl`, `grants`, `version`, `lineage`, `status`, `store_ref`, `schema_version`. Every field has a one-line meaning in `docs/glossary.md`. `make api` fails CI on a dirty diff.

Amendments made when deciding:

- Implemented in step-0 task S0.7 (`packages/core/src/schema.ts`) following `docs/architecture.md`: scope is the string `person:<id>`, `role:<id>`, `team:<id>` or `org`; `ttl` is in seconds; `store_ref` is `{adapter, key}` or null; a grant is `{to, class?, mode, expires?}`.
- MemoryItem is a union on `class`: procedural content is `{body, tools}`, other classes carry text or a structured payload. A fixture showed a procedure without a tool list passing as a generic payload.
- A MemoryEvent carries the `item` it produces, for replay, and optional `usage`. `schema_version` starts at 0.
- Python types are TypedDicts generated by datamodel-code-generator; `make api-check` fails on a dirty tree.

Amendments made in the review fix pass, 2026-10-25:

- Decision D1 (review finding R2-2 on PR #2): `store_ref` does not identify an item. Several versions of an item, each a new item id whose `lineage` names the version it supersedes, may live under one store_ref (Adapter.history), and a retired item keeps its ref. Migration 2's index on (store_adapter, store_key) is therefore not unique; it was edited in place because PR #2 was unmerged and nothing had been persisted. `itemByStoreRef` returns the latest active holder of the ref (highest seq among items not retired), else the latest holder, else nothing. The schema itself is unchanged.
- Refinement of D1 in review round 2, 2026-10-28 (finding N1): the latest active holder is the newest version, not the most recently touched item. Among the holders not retired, a holder is superseded when another of them names it in its `lineage`, followed through every projected item; `itemByStoreRef` returns the holder no active holder supersedes, the highest seq breaking ties, and falls back to the highest seq among the active holders when a lineage cycle leaves none. Updating a superseded version in place (for example setting its `valid_to`, ADR 0005 option (a)) no longer makes it the holder. A retired holder's lineage supersedes nothing, and with no active holder the latest holder by seq is returned, as before.

Amendments made by the schema version 1 PR, 2026-11-06 (branch `schema-v1`, step 8 of the post Gate B plan):

- `schema_version` is 1. A read event carries `item_ids`, the ids of the items it returned in rank order (absent on other ops), so utility replays from the log (ADR 0025, finding P4-5). `ProvenanceKind` gains `external` (ADR 0004's amendment of the same day). Policy documents say `schema_version: 1`; the bundled presets and the fixtures were bumped by command.
- Migration 4 upgrades a version 0 log in place on SQLite and Postgres: every stored event, item, explanation and carried item says version 1, and each read event's `item_ids` are its explanation rows in rank order (migration 3 wrote one per returned item in the read's own transaction). No other field is rewritten (`packages/core/test/db/schema-v1.test.ts`). A version 0 policy file no longer loads and is bumped by hand; there is no reader of version 0 records after the migration.

Amendment made by card E2.8, 2026-11-21 (branch `e2-8-policy-schema`), accepted under the lead's delegation of that day (`docs/tasks/lead-decisions.md`, "Decided on 2026-11-21, under the lead's delegation", row "E2.8, the schema version"):

- Decision D2: a named exception to AGENTS.md rule 5, for contracts that are never persisted. Today that is the policy document alone: it is not stored in the log (`packages/core/src/db/migrate.ts`, migration 3's note that the policy in force is not in the log), and it is parsed only by `parsePolicy` (`packages/core/src/policy/load.ts`) and by the fault set's `readSetPolicy` (`packages/runner/src/lint-fault-set.ts`). A field added to such a contract that is purely additive, optional and without a default, whose absence parses and serialises byte for byte as before, needs no `schema_version` bump and no migration. The change is still its own PR, with `make api` and the fixtures. The next breaking change to the policy bumps the version.
- The exception does not reach a persisted contract. Any change to MemoryItem, MemoryEvent, LintFinding or Explanation still bumps `schema_version` and adds a migration, as rule 5 says: the additive `item_ids` of version 1 needed migration 4, because MemoryEvent is persisted. AGENTS.md rule 5 gains one sentence naming the exception.
- Applied first to the policy's `content_guards` block (ADR 0039) and `trust` block (ADR 0040), each option in them optional too; `schema_version` stays 1. Until the card that enforces an option lands, the loader refuses any value of it but `off`, naming that card (E2.9, E2.10 or E2.11), so no policy sets a guard the plane ignores.
- Why. The policy shares `SCHEMA_VERSION` with items and events. C3 and C4 embed the parsed policy, `schema_version` included, in their prompts (`policyInstruction`, `packages/runner/src/conditions.ts`), and the cache key hashes the prompt, so a bump would move 46 committed cassette keys (`fixtures/cassettes/x1-h1-gatemem`, `x1-h1-mem-inv`, `x1-h1-gatemem-rag` and `rn1-gatemem-probe`). It would also move the fault set's `policy.json` and `states.jsonl`, whose hashes `research/configs/h3-lint-model.json` pins. Both are registered, nine days before the `prereg-v1` tag (`docs/log/2026-11-21-e2-8-version-bump-moves-cassette-keys.md`).
- Cost. Code built before the change rejects a policy file that uses the new blocks, since the policy is a strict object. Every reader (core, the generated clients, the Python types) is in this repository and ships in the same PR.
- Checked by `packages/core/test/unit/policy/presets.test.ts`: each registered preset parses to the sha256 it had before the change.

Use of decision D2 by card E2.14 of the second absorb plan, 2026-11-28 (branch `a2-e2-14`): the policy gains the optional `lints.model` (`evidence`), `procedures` (`safety_scan`, `drift`), `consent`, `erasure` (`mode`), `approval` and `grants` (`expiry_cap`) blocks, each option without a default, so `schema_version` stays 1 and every registered preset parses to the same sha256 (`packages/core/test/unit/policy/load-options.test.ts`). Nothing builds them yet, so the loader refuses every present value, `off` included, naming the card that builds it (L9, D5, D4, E9.12, E9.13, E2.19, E2.21); each card lifts its own refusal.

## Alternatives considered

(a) Zod 4 as the single source, JSON Schema via `z.toJSONSchema`, Python types generated from the JSON Schema. (b) JSON Schema hand-written, codegen both ways. (c) TypeBox.

## Consequences

Unblocks E0.2, every adapter, the Python analysis types. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.
