# ADR 0027: One HTTP contract for every surface: a route table, generated OpenAPI and client, loopback only until authentication

Status: accepted, 2026-11-02
Deciders: Omar (lead)
Supersedes: nothing; it gives ADR 0001's "the HTTP server is thin, clients are generated from it" and ADR 0022's MCP surface their mechanism.

## Context

ADR 0001 makes the HTTP server a thin TypeScript layer over core with clients generated from it; cards E8.1 to E8.6 build the server, the client, the CLI and MCP server on that client, and the inspector. Until now the CLI calls core directly (the Gate A slice of E8.2). Four questions were open: how the OpenAPI document is produced without a second source of truth beside the Zod contracts; how the CLI can call a client without needing a running server; who the caller is, when there is no authentication yet; and what a browser page on the same machine can do to a server listening on localhost.

## Decision

1. **The route table is the single source.** The server is a Hono app. Each route is one entry naming its method, path, request and response Zod schemas (reusing core's contracts) and a handler that calls the Plane or another core function and holds no policy logic (rule 1). OpenAPI 3.1 is built from the table with Zod 4's `z.toJSONSchema`, not an OpenAPI plugin whose Zod range would have to track core's, and `make api` writes it to `sdk/openapi.json`.
2. **The client is generated.** `openapi-typescript` turns `sdk/openapi.json` into types and `openapi-fetch` is the run-time client; `make api` writes `sdk/ts/` and `packages/ui/src/api/`, never edited by hand, and `make api-check` covers them.
3. **In process by default.** The CLI and the MCP server call the client. With no server named, the client's fetch is bound to the app (`app.fetch`) over the local workspace, so no command needs a running server and every command is still one client call; `--server <url>` or `ENGRAM_SERVER_URL` sends the same calls over HTTP. `doctor` stays local: it checks the machine.
4. **Loopback only until authentication.** The server listens on 127.0.0.1 or ::1 and refuses any other host; it checks `Host` against loopback names (DNS rebinding), refuses an `Origin` other than its own, accepts only `application/json` bodies (a cross-site browser request with that type needs a preflight, which gets no CORS headers), and caps body size. `docker-compose.yml` gains no `server` or `ui` service until a card adds authentication.
5. **The actor is in the request and self-asserted**, as the CLI's `--as` is; the "CLI identity" follow-up covers both. The MCP server fixes its actor at launch with source `model`, and no tool parameter names an actor, a source or a provenance kind (ADR 0004, decision D4).
6. **A decision is a response, not an error.** Allow, deny and ask are 200 with the event; `InvalidCallError` is 400, `ExplainDeniedError` 403, `NotImplementedYet` 501 naming the card.
7. **The inspector reads through the plane.** It views as one actor; scope lanes come from `Plane.read` as that actor; the timeline shows `visibleEvents(actor, events)` (a pure core function: events in the viewer's member scopes and events the viewer made); the explain view uses `Plane.explain`, so only a read's own reader sees its explanations (decision D5). The read event's filtered counts are parsed by a core function beside the one that writes the reason.

Amendments made in PR 3 of the plan (cards E8.1, E8.3, E8.2, E8.4; branch gb-pr3-surfaces, 2026-10-29):

- The table lives in packages/server/src/routes.ts, the schemas in contract.ts, the guards and error mapping in app.ts. Statuses the decision left open: `UnknownReadError` (new in core, thrown by explain for an id that names no read) is 404; a store call in a workspace with no store (`NoStoreError`) is 503; a request failing its schema or not JSON is 400; a refused Host or Origin is 403; a body that is not application/json is 415; a body over 1 MiB is 413; an unknown route is 404. Every error body is `{ error: { code, message, card? } }`; a 500 carries `internal error` only, and its error goes to `onError` (the server's stderr, or the CLI's in process).
- The JSON-body rule covers POST, PUT and PATCH; GET, HEAD and DELETE carry no body. The rules are one middleware, `loopbackGuard(port)`, which the MCP server's streamable HTTP endpoint also runs behind. The Host must be `127.0.0.1`, `localhost` or `[::1]` with the server's port, in the Host header and in the URL the app sees; `engram serve --host` accepts `127.0.0.1`, `::1` and `localhost`. The default port is 7313.
- `at` is optional in every request; the server fills it from its injected clock (the CLI's and the MCP server's `now`). Core still reads no clock.
- The write request's `item` is any JSON object, documented as a MemoryItem: the plane validates it and records an invalid one as a deny event (engram/write/schema), so the HTTP layer does not refuse it first. In the generated TypeScript types `JsonValue` is `unknown`, because openapi-typescript renders the recursive component as a type that names itself (TS2502).
- The read route runs what `engram read` ran before, so the CLI stays one call: when the workspace has a store, the store owner's retention sweep, then adoption of the store's own memories (ADR 0025, decision D8), then `Plane.read` as the caller; the response carries their reports as `sync` and the policy label as `policy`. `sync` goes back only to the store's owner (`person:<owner>`); every other reader gets null, since the report names the owner's item ids, reasons and a content hash (corrected in the review fix pass, finding R3-3).
- `visibleEvents` (packages/core/src/visible.ts): an event is visible to the actor who made it and to a member of its source or target scope. Read and bypass_blocked events carry no scope, nor does a write denied by the schema rule before a valid scope was known; those only their maker sees. A promotion refused for an item the promoter cannot access withholds its source scope and keeps its target, so members of the target see it. An event leaving a member scope (a promotion out of it, the retire that supersedes the source) is visible to that scope's members. Membership decides which events show. What each shows (review finding R3-4): an event's `item` is kept only when the read filter (`evaluateRead`) would return that item to the viewer at the request's time, both as the event carries it and as the projection holds it now, so an item in a scope the read matrix keeps from the viewer, retired, past its ttl or outside its validity is withheld and the rest of the event kept. `visibleEvents(viewer, events, { policy, at, current })` takes the policy, the time and the projection for this. `POST /events` takes the viewer, an optional `after` seq and an optional `at`.
- The client: `make api` runs packages/server/scripts/api.ts, which writes sdk/openapi.json, sdk/ts (package `@engram/sdk`, a workspace package: package.json, src/schema.ts by openapi-typescript, src/index.ts with `createEngramClient({ baseUrl, fetch })` over openapi-fetch) and the same two source files into packages/ui/src/api. openapi-typescript needs the TypeScript compiler API, which TypeScript 7 does not ship, so packages/server pins TypeScript 5.9.3 as its peer; type checking stays on 7.0.2.
- The workspace opener is packages/server/src/workspace.ts. It loads the policy and builds the store at once and opens the log on first use, so a route whose Plane method has not landed (lint, simulate, distill) never opens a log; the CLI opens it before its call, so a log problem prints as it always did. `--owner` alone opens no store (explain, retain and the hook take it as the actor); `--root` or `--store` does. `engram serve` without `--root` serves the log alone, and a write answers 503.
- In process, the client's base URL is `http://127.0.0.1:7313`, a label that never reaches a socket, so the guards hold there too. With `--server` or `ENGRAM_SERVER_URL`, the CLI refuses `--db`, `--root`, `--store`, `--policy` and `--import-valid-from`, which name the server's own workspace. `engram lint` sends scope `org` unless `--scope` names one; `engram simulate` sends an empty workload unless `--workload` names a file.
- Review fix pass (findings R3-11 and R3-12): after binding, `listen` and the MCP server's HTTP transport check that the bound address is loopback (127.0.0.0/8, ::1, or mapped 127) and close the socket if it is not, since `localhost` is resolved by the system; the MCP HTTP endpoint has the same 1 MiB body cap as the API.
- The viewer of `GET /viewer` is `engram serve --as` with `--member` and `--level`, built as the CLI builds actors, without a source.

Amendments made by cards E8.5 and E8.6, 2026-10-29 (branch `gb-pr4-inspector`, PR 4 of the Gate B plan):

- The inspector's stack: Vite 8.3.4 (the version vitest already runs on) and React 19.3.1, with no `@vitejs/plugin-react` (Vite's own transform compiles TSX as `packages/ui/tsconfig.json` says, and a production build needs no fast refresh), no router, no state or CSS library, system fonts only. `make ui` builds it into `packages/ui/dist`. TypeScript 7 checks it under `make lint` through `packages/ui/tsconfig.json` (DOM library, `react-jsx`); the root tsconfig excludes `packages/ui`.
- Serving: `createApp` takes a `ui` directory and serves it at `/` for GET and HEAD outside `/api/v1`, after the Host and Origin guards, and never for a path in the API's space (any path whose first segment, decoded once and compared without case, is `api`: those get the API's JSON 404); `listen` passes the built `packages/ui/dist` when it holds an `index.html`, so `engram serve` serves the inspector with no flag. A path is decoded once and refused with a backslash, a NUL, a `.` or `..` segment or a segment holding `:` (a drive or a stream on Windows), and the file must resolve, links followed, inside the directory; a path without an extension that names no file gets `index.html`. Every inspector response carries a same-origin Content-Security-Policy (`default-src 'self'`, `connect-src 'self'`), `nosniff` and `no-referrer`. With no build, `/` answers 404 naming `make ui`.
- The counts: `formatReadReason`, `parseReadReason` and `readCounts` live in `packages/core/src/plane/read-reason.ts`; the explain route returns `counts` (the `ReadCounts` component) beside the explanations, null for a reason the plane did not write in that form; the route finds the event by id (core's `eventById`), not by loading the log. The counts, `out_of_reach` among them, are audit data for the human inspector: `out_of_reach` counts items outside the reader's reach, which decision D5 keeps from the reader, so a surface that answers a model does not pass them on. The MCP server's `memory_explain` returns the explanations only, and a test holds it to that (`packages/mcp/test/explain-audit.test.ts`).
- Another actor's read: reads name no scope, so `visibleEvents` never lists another actor's read. The explain view meets one when the viewer changes while a read is selected; it shows the event and the line that only its reader may explain it, without calling explain, and a 403 renders the same line. Any other selected event stays on a viewer change only if the new viewer may see it, and the timeline's filters reset. The explain view's item text is the item's text in the current lanes, labelled so, not its text at the read's time.
- Each load of the lanes is one read as the viewer at the server's clock, so it appends a read event the timeline then shows (decision 5 accepts this: a read that left no event would bypass rule 2).
- Layer 6 drives Chromium through the `playwright` library (1.64.1) from vitest; `pnpm exec playwright install chromium` provides the browser, and the e2e workflow installs it with its system libraries.

Amendment made by card RV7, 2026-11-20 (branch `rv7`, core review finding RV-CORE-4). Status: proposed, for the lead's acceptance: `visibleEvents` shows an event to a member of its source or target scope only when the read matrix lets the member's level read that scope (`readableScope`), and to its maker as before. Membership alone no longer decides: a member the matrix stops from reading a scope sees none of its events, where the amendment of PR 3 above showed them with the item withheld. The route's description in `packages/server/src/routes.ts` ("those in its member scopes") still says membership; card RV5 edits that file, and the words follow when it lands.

## Alternatives considered

- `@hono/zod-openapi` or Fastify with a Zod type provider: a second schema layer pinned to its own Zod range; the table plus `z.toJSONSchema` is a few dozen lines over the contracts core already exports.
- A CLI that requires a running server: every command would fail without `engram serve`, and the per-user SQLite log (decision D9) would gain a daemon.
- Lanes from the projection (`itemsAt`): faster and time-travelling, but a read that bypasses the read filter and leaves no event (rule 2); snapshots wait for E8.10.
- Binding any host with a warning: no authentication means any device on the network could write as anyone.

## Consequences

Unblocks E8.1 to E8.6 and the MCP handshake of layer 6. A shared Postgres log is not served to other machines until authentication exists. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.

Amendment made by card E8.9, 2026-11-06 (branch `e8-9-simulator`, ADR 0032, accepted 2026-11-19):

- `/simulate` takes core's `Workload` (actors and recorded calls) and an optional candidate `Policy`, and answers core's `SimReport`, both named components of `sdk/openapi.json`; it no longer answers 501. The baseline is the workspace's policy. It replays on scratch logs and stores, so like lint and distill it never opens the workspace's log, and a workload that fails its shape or names no actor for a step is 400 (`invalid_call`). `engram simulate` sends the candidate `--candidate` names, loaded as `--policy` is.

Amendment proposed by card RV5, 2026-11-20 (the repository review of the surfaces, findings RV-SRF-1 and RV-SRF-2). Status: proposed, for the lead's acceptance; drafted by the card's agent. It replaces "`at` is optional in every request; the server fills it from its injected clock" (the PR 3 amendments) and the read route's sync paragraph where they differ.

- **The server stamps every event's `ts` from its own clock** (RV-SRF-2). Before, a request's `at` became its event's `ts`, so a caller chose the time every decision was judged at: a read backdated to 19:49:30, made at 19:50:17, returned an item through a grant that expired at 19:50, and the dogfood report, judging the read at its `ts`, counted no violation. Authentication (decision 4) would not have closed it, since an authenticated caller could still name any time. Now no request but a read has `at`: the write, check, promote, grants, retain, lint, events and bypass schemas dropped the field, so a request that sends it fails its strict schema (400, `bad_request`) and appends nothing.
- **A read's `at` is a read-only `valid_at`.** It moves only the time validity windows are judged at (ADR 0005: what was true at that time). Status, ttl, grant expiry and scoring are judged at the server's clock, the read event's `ts`, so a named time cannot reopen what a grant's expiry or a ttl closed (`evaluateRead(policy, actor, item, at, validAt)`, `ReadQuery.valid_at`). It sweeps nothing. It is recorded apart from `ts` with no schema change: the read event's reason ends `; validity windows judged at <time>` (`formatReadReason`, parsed by `readValidAt`), and each explanation's `validity.at` is that time. The twin dogfood's report judges a read's scope, grants and ttl at its `ts` and its validity window at the recorded `valid_at` (`packages/core/src/dogfood.ts`), so an honest `valid_at` read is no false violation.
- **The CLI and the MCP server follow.** Over `--server` (or `ENGRAM_SERVER_URL`), `engram write`, `promote`, `retain` and `lint` refuse `--at` (a usage error, exit 2); in process the CLI is the server (decision 3), and its clock is the real one: `--at` is refused there as well unless `--test-clock`, a flag for tests and fixtures only, is given, in which case it sets the clock for that one call (review fix pass of PR #59, RV5-3: `retain --at <future>` retired the member's own items for good, and a backdated write was stamped before the log's history). `engram read --at` is the read's `valid_at` in process and over `--server` alike, and the line it prints shows the read's `ts` and, when given, the validity time. The MCP server sends no time; its memory_simulate workload records each call at the `ts` its event got. The Claude Code hook sends none to `/bypass`.
- **The read route's sync** (RV-SRF-1) is core's `syncBeforeRead` (`packages/core/src/plane/before-read.ts`; ADR 0025's amendment of RV5): the store's scope is swept as its owner only when the owner reads, at the server's clock; the store's own memories are adopted as the owner whoever reads; core returns what the reader may see, and `sync` is non-null for the owner only, as before (R3-3).
- **In core too** (finding RV-CORE-3 of the core review): a read's access time is never earlier than the log's head, the latest `ts` the log holds whatever the order its events were appended in (ADR 0005, amendment of RV5, and its review fix pass), so even a server clock that runs behind the log, or a caller of the Plane that names an earlier time, cannot reopen an expired grant or ttl; the timeline route judges its items at the same `accessTime`.
- Not decided here: refusing a `valid_at` beyond a bound from the server's clock, which the review offered as the other design. Nothing is judged at `valid_at` but validity windows, so a far `valid_at` reveals only what was true then within what the reader may read now.
