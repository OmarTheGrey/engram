# ADR 0007: Write gate rules and source isolation

Status: accepted, 2026-11-02
Deciders: Omar (lead)
Supersedes: the proposal of the same number in `docs/decisions/README.md`

## Context

MPBench (aggressive write policies are easier to poison; weak-signal attacks evade detectors); MemSecBench (adoption is the bottleneck, so blocking at write is cheaper than catching at read); Mem0's ADD, UPDATE, DELETE, NOOP as the interception point.

## Decision

(a) at the gate; model-based checks are lints that run after the write and can retire. The gate is deterministic so the H1 condition "enforcement" has no model in it. Every MPBench attack class maps to a rule or a lint in `fixtures/faults/`; classes with no deterministic defence are listed in the thesis as such.

Amendments made in the review fix pass, 2026-10-25 (PR #5, findings R5-1 to R5-14):

- Decisions D4 and D6 (findings R5-3 to R5-7, R5-14, PR #5): the gate's checks, in order, are membership (`engram/write/membership`), rewrite owner and version (`engram/write/version`), grants (`engram/write/grant`), then the policy rule of the scope level (default deny `engram/write/default-deny`, forbidden class, listed source, source isolation, confidence floor, review). Provenance is set from the actor's harness-set source before the gate (ADR 0004).
- Decision D6: every outcome of a write is an event. An invalid actor or time is refused with `InvalidCallError` before the store or the log is touched, since no event can carry an invalid actor id or timestamp; an invalid item is a schema denial event as before. If the adapter throws after an allow, or returns a ref that is malformed, belongs to another adapter, or is already held by an item outside the written item's lineage, the plane appends one deny event (`engram/write/store-failure`, reason with the error) and rethrows; the store may hold bytes the plane never projects, and the event says so.

Amendments made in round 2 of the review fix pass, 2026-10-28 (PR #5, verifier findings N2 to N4):

- Finding N2: writes over one db handle run one at a time, in call order, through an async queue in `gatedWrite` (packages/core/src/plane/write.ts); a failed write does not stall it. Chosen over re-checking the projected item inside the event transaction because the re-check runs after the adapter has written: a losing write would already have replaced the winner's bytes in the store (the fake and the files adapter key by item id), leaving the log honest but the store wrong. The queue stops the losing write before the store. Reads are not queued; each takes the projection once, synchronously. Limit: writers in another process sharing one log file (the CLI beside a pi session on `<home>/.engram/engram.db`) are not serialised by it.
- Finding N3: when the projected item of the written id lies in a scope the writer cannot read (by membership and the read matrix), the denial's reason is "the item id is held by an item you cannot access" and names no scope, owner or version. The reason travels in the WriteResult's event, which the pi extension shows to the model, so the detail is kept out of the event as well. The policy_id still names the deciding rule (rule 3).
- Finding N4: the plane cannot prevent a store from writing at a ref another item holds, since refs are the adapter's and not predictable before the write. The adapter contract already forbids it (the conformance suite's "two item ids are two items under two refs" and "write is idempotent per item id"), so only a non-conforming store reaches this; the store-failure event's reason now says the store broke the contract, that the bytes it wrote for the item are orphaned and never projected, and that they may have replaced the other item's record in the store.

Amendments made in the review fix pass, 2026-10-25 (PR #6, findings R6-2 to R6-4):

- Decision D8: adoption (`adoptStoreItems`, packages/core/src/plane/adopt.ts) puts what a store already holds through this gate as the store's owner, not as whoever reads: the CLI passes `{ id: person:<owner>, level: person, memberships: [person:<owner>] }`, and adoption sets `source: import` itself whatever the caller passed. Every adoption event's reason starts "adopted from store <name>: ". An allowed item is recorded at the store_ref it already has, through the same ref checks and store-failure event as a written one. When a projected item of the store's scope is no longer listed, or the store's version of it is denied, the plane retires the projected item with one event (op retire, decision allow, policy_id `engram/adopt/retract`, reason naming why), so it never serves content the store no longer has. A denied item is not gated again while its hash (of the store's item, status aside, recorded at the end of the deny event's reason) is unchanged; a retracted item the store holds again is gated again; an item retired by anything other than adoption is not brought back while the store has it unchanged.

Amendments made in the review fix pass, round 2, 2026-10-29 (PR #6):

- An item the store can no longer read (it reports the key through `Adapter.diagnostics`, ADR 0013) is retired, and its retire reason says the store can no longer read it and names the store's diagnostic, instead of "no longer in store". It is retired rather than kept because the plane must not serve content the store no longer holds in a readable form: the store's own read of the entry throws, and what the plane holds is a version the store has since changed. When the entry is readable again it is gated again, as any retracted item the store holds.
- Adoption compares the store's item with the projected one, and hashes it for the deny note, without the fields the adapter reports through `derivedFields` (the files adapter's modification-time `valid_from`). Touching a file therefore adds no write, retire or deny event; the projection keeps the `valid_from` of the version it adopted. A change to a field the store stores, `valid_from` in an Engram file's frontmatter included, is still gated again. A log whose deny notes were written before this change gates such a denied item once more, then records the new hash.

Amendments made in the review fix pass, 2026-10-25 (PR #7, findings R7-1 to R7-15):

- Decision D12 (findings R7-3, R7-4): in a pi session the gate decides in `tool_call` and commits in the tool's `execute`. `Plane.checkWrite(actor, item, at)` gives the decision `write` would give, computed by the same code, with no store write and no event; a deny is then committed in `tool_call` (one deny event) and blocks the call with the Plane's reason. An allowed write is committed by `Plane.write` in `execute`, from the arguments execute receives, so a call that a later handler blocks or that is aborted before it runs never reaches the store or the log as allowed. No pending state is kept between the two: each execute builds its own item, so two calls sharing a tool call id are two writes with their own results (D12 asked for pending state keyed by tool call id; with none, the case cannot cross).
- Decision D4 as the extension applies it: the agent's writes carry the actor's source `model`, so the plane sets the provenance kind and actor.

Amendments made when implementing card E2.4, 2026-10-29 (ADR 0025):

- The write queue of finding N2 is its own module, `inWriteQueue(db, task)` in packages/core/src/plane/queue.ts, shared by every Plane call that changes items: `Plane.write` and `Plane.retain` now, `Plane.promote` (card E2.5) next. After a landing write, its budget check (ADR 0025) runs in the same queue slot, so no other write or sweep interleaves between the write and its evictions.
- The gate gains a check after the confidence floor: a `model`, `compaction` or `tool` write whose normalised content hash equals that of an item retired in its scope is denied with `engram/write/retired-content` (ADR 0025, decision 5). `Plane.checkWrite` gives the same decision.

- Review fix pass of PR 4 (findings P4-3 and P4-8, and the review's note on adoption): a call to `inWriteQueue` from inside a task on the same db rejects with `NestedWriteQueueError` instead of waiting for itself and stalling the log's queue; inside a task the in-slot primitives are `enforceBudget` and `appendEvent`. Adoption's retractions are appended inside the write queue, reading the projection again there. The retired-content check counts only items an allowed retire or evict event retired, never one written with status `retired`.

- Verification of PR 4 (findings P4-13 and P4-16): the nesting guard refuses a call only while the slot whose async context it was made from is still running, so a callback created in a slot that fires after it ended queues normally. The retired-content check also ignores retirements by the item's own ttl (`engram/retention/item-ttl`), which its writer chose (ADR 0025).

Amendments made by card E2.6, 2026-11-19 (branch `e2-6`; proposed, for the lead's acceptance). They supersede the limit finding N2 recorded ("writers in another process sharing one log file are not serialised by it"):

- Writers on different db handles over one log (two processes, such as `engram serve` beside an `engram read` on one workspace) are ordered by the log's lock, which a `Db.transaction` holds (BEGIN IMMEDIATE on SQLite, the advisory lock on Postgres; ADR 0024), and every operation that writes the store and then appends to the log follows one protocol (`packages/core/src/plane/commit.ts`): decide on the projection, noting the log's head (its last seq) before reading it; write the store; then, in the transaction that would append the allow, check that no event that may change the item (op write, update, promote, retire or evict, of any decision) was appended after that head, and that no offboarding of its person scope began after it. A decision that fails the check is stale: nothing is appended there; the store is put back as the log has it (the record deleted when the item is gone, erased or being erased, the projected item written back otherwise), and in one more transaction, which first checks that nothing changed the item since the state it wrote was read, the deny event is appended; if something did, the store is put back again, at most eight rounds. The deny comes after the store is put back so that a writer whose decision preceded it sees it as a change and puts the store back in turn, and an adoption that listed the store before it leaves the record to its next listing. Rules: `engram/write/conflict` (`Plane.write`), `engram/grant/conflict` (`Plane.changeGrants`, ADR 0034, decision 5, now on this protocol), `engram/promote/conflict` (`Plane.promote`, in place and as a new version), `engram/offboard/conflict` (a handover; the item is then handed over again as it now stands, at most four times, so an owner's change made meanwhile is kept). The budget check after a landing write or promotion runs in the same transaction as its event. Chosen over holding the log's lock across the store call, which the synchronous Db contract (ADR 0024) cannot express and which would make every other process wait on the slowest store (SQLite gives up after five seconds), and over a lease table beside the log, which is a migration (AGENTS.md rule 5); the log alone carries the protocol, and no adapter gains a capability.
- An offboarding marks its erasure before it deletes any store record: one event (op retire, no item, `engram/offboard/begin`), appended in the transaction that reads what will be erased and handed over; its report event (`engram/offboard/report`) closes it. While it is open, a write, grant change, promotion or adoption into that person scope that the gate would allow is refused (`engram/offboard/erasing`), and one decided before the mark finds it in its check. So every store write for an item that is erased is either deleted with it (it landed before the erasure deleted the record) or deleted by its own writer (it landed after, and its check follows it). Chosen over deleting every erased ref a second time after the erasure commits, because that leaves a window after the second pass in which a write still in flight lands, and a crash between the commit and the second pass leaves the record; with the mark, a crash between the mark and the report leaves the person scope frozen, not leaking, until offboarding runs again and completes. ADR 0010's one hard deletion keeps its guarantee.
- A write under the id of an item an offboarding erased, which the projection no longer holds, is refused (`engram/write/erased`); the reason names the erased scope only to a member of it (finding N3). Adoption refuses a record under such an id (`engram/adopt/erased`) unless the erasure left that record in a store that refuses the plane's delete and its content has changed since (ADR 0010's amendment of 2026-11-13): any other record under an erased id is a store write that was in flight during the erasure, or a restored copy.
- Adoption decides and commits each record in one transaction, in the write queue. It notes the log's head before it lists the store; a record whose item the log changed after that head, or whose person scope an offboarding began erasing since, is left to the next adoption with no event (counted under `unchanged`), and so is the retraction of such an item, so a listing older than a committed change neither undoes it nor retires the item. A retention sweep decides and commits in one transaction as well.
- Review fix pass of PR #50, 2026-11-19 (findings P50-1 to P50-8), replacing the limits this amendment first recorded:
  - An adoption of a stale writer's bytes (P50-1, ordering RV8). An adoption can list a writer's bytes after they land and before the writer's check, and record them as the owner's import. Two cases. When the writer's decision still stands (nothing else changed the item), the adoption recorded the writer's own write seen early, so the writer's check ignores it and its allow replaces the import provenance. When the decision is stale, settling withdraws the adoption: if every allowed change to the item since the first adoption event about those bytes (an allow recording them, or a deny of them followed by a retraction) is an adoption's, the item is put back as it stood before that event, by one allowed event (`engram/adopt/withdrawn`) appended with the writer's deny, and the store is given that version. So a removed grant never comes back through the owner's import of a stale write. Chosen over recording an intent event before every store write, which would add an event to every write (invariant 3 counts exactly one) and leave a crashed writer's intent open for good, and over refusing any adoption that differs from the projection at the same version, which would refuse an owner's hand edit too.
  - A writer that throws or crashes between its store write and its commit, or whose repair's store call fails (P50-2, orderings RV3 to RV5). Adoption deletes, after committing its refusal, a record under the id of an item an offboarding erased (unless the erasure left that record in a store refusing the delete, where ADR 0010's content rule stands), and a record in an offboarded person scope (one with a completed offboarding and none open) under an id the log never allowed (`engram/adopt/offboarded`): a write that never committed. A transient delete failure appends a store-failure deny, so the next adoption tries again; a permanent refusal leaves the record refused. Such a record is gated again even when an earlier refusal of the same bytes stands. So erased or never-committed content in an offboarded scope lasts until the next adoption, which `engram read` runs before every read.
  - What counts as a change (P50-4, RV7): an allowed event, or one of the plane's own denies that follow a store write whose decision did not stand (a conflict, a store failure, an adoption's deletion); a gate's deny changes nothing and makes no decision stale.
  - Each begin mark is closed by the report naming it (P50-5, RV1b): a second offboarding's report no longer reopens the scope while the first is still erasing. A report from before this clause closes every mark before it.
  - A handover that conflicts on every attempt (P50-3, RV2) ends with one deny (`engram/offboard/not-handed-over`), listed in the report's `not_reached` and counted in its reason; the last conflict's reason says no further attempt is made.
  - Adoption counts a record left to the next adoption under `deferred`, not `unchanged` (P50-7); the HTTP contract and `engram read`'s output carry it.
  - A model lint awaited across an erasure on another handle drops every finding about an item erased after its snapshot, or naming its id or the content hash of the version it read (P50-8), so the erasure's redaction of lint evidence is not undone.
- Tests: `packages/core/test/unit/plane/cross-handle.test.ts` (the verification of PR #44's orderings R1 to R9 and the orderings R10 to R15 this card found, on SQLite and embedded Postgres, two handles each), `packages/core/test/unit/plane/cross-handle-review.test.ts` (the review of PR #50's orderings RV1 to RV9 and the model lint across an erasure), `packages/adapters/test/plane/cross-handle-files.test.ts` (the files adapter, two handles on one log file), and invariant 1's walk across two handles in `packages/core/test/property/invariants.test.ts`, which also crashes writers at their commit and at a repair's store call.

## Alternatives considered

(a) Deterministic rules only: source kind, scope, class, provenance presence, hash, size, and a per-scope budget. (b) Add a model-based classifier at write time.

## Consequences

Unblocks E2.2, L2, the MPBench arm. Changing this decision needs a new ADR that supersedes this one and a `decision` log entry.
