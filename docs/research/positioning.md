# Positioning: what is new in Engram, and its two nearest neighbours

Written 2026-11-21 by card R3 of the absorb plan (`docs/tasks/R3.md`). It states the novelty claim once, so the README, `docs/architecture.md` and the thesis can point here, and it says exactly how Engram differs from HEAMS (arXiv 2611.20144) and SAFE-Mem (arXiv 2610.22959). Every difference cites where it comes from in the paper or the code, and where in Engram's code or ADRs the Engram side is true. The framing sentence in `docs/research/preregistration.md` is outside this card: changing it is the lead's amendment.

## The claim

To our knowledge, Engram is the first deterministic, event-logged, replayable control plane across memory stores, with a pre-registered measurement of its governance tax.

Each word is a condition, and the claim is only as strong as the weakest:

- **Deterministic.** Every write and read decision is a pure function of a typed policy, the actor, the item and the time, evaluated by code (ADR 0006; `evaluateWrite` and `evaluateRead` in `packages/core/src/policy/evaluate.ts`). The plane never calls a model (AGENTS.md rule 4); `packages/core` has no import from pi-ai.
- **Event-logged.** Every decision appends a `MemoryEvent` carrying the actor, the scope, the decision, a `reason` and a `policy_id` (`packages/core/src/schema.ts`, `MemoryEvent`; ADR 0003), and is mirrored into the pi session as a custom entry (AGENTS.md rule 3). The log is the source of truth: item state is a projection of it (ADR 0003).
- **Replayable.** The item set as it stood after any event is rebuilt from the log alone (`itemsAt` in `packages/core/src/replay.ts`; tests in `packages/core/test/replay/`), and a recorded workload replays every decision through the plane's own code under any policy (ADR 0032; `packages/core/src/plane/simulate.ts`). The limit is stated in ADR 0032 itself: events alone cannot be decided again, because a denied write's event carries no item and a read's event carries no query. Replayable reads from the log alone are a later plan (R-072 in `docs/research/absorb/long-list.md`), not a present property.
- **Across memory stores.** One adapter contract (`Adapter` in `packages/core/src/adapter.ts`; ADR 0013) with one conformance suite (`packages/adapters/test/conformance/`, and the Letta adapter's `packages/adapters/test/letta/`), and three adapters: files, Mem0 and Letta (`packages/adapters/src/`). Store independence is a design property: no condition uses a store's own search, so the plane alone decides what reaches the model (ADR 0031, decision 2; ADR 0035). ADR 0035 asks for a request-identity check that compares the sha256 of every model request across adapters; that check is not built yet and has no row in `research/results/MANIFEST.md`. The registered H1 runs use one store, Mem0 (`docs/research/preregistration.md`, H1 stopping rule).
- **Pre-registered measurement of its governance tax.** H2 registers the cost of enforcement in utility and tokens at three presets against ungoverned memory and no memory (C1, C2, C5), and H1 registers enforcement against telling the model the policy (C3, C4 against C5), on seeded, cached calls (`docs/research/preregistration.md`, H1 and H2; ADR 0017). Neither has run: the H1 live runs start on 2026-12-01. The claim is about what is registered, not about a result.

What the claim no longer says, and why:

| Withdrawn or narrowed | Because |
|---|---|
| The first governance layer over existing memory stores | HEAMS ships one: a wrapper that applies retention and recall policies around any memory system behind its common interface (Sec. 4.2; `PrivacyMemoryWrapper` in the repository's `memory_plugins/heams_memory_privacy_wrapper/src/heams_memory_privacy_wrapper/wrapper.py`). |
| The first measured governance tax | Both neighbours measure a trade-off: HEAMS reports a 4.80 point helpfulness cost of recall governance (Table 5) and a fall in permitted recall from 100.00 to 84.47 percent under retention governance (Table 7); SAFE-Mem reports what admission costs against its own memory without it (Appendix G). What is still Engram's is that the measurement is registered before it runs, against instruction baselines, on three models. |
| The first to log each decision with its reason and rule | HEAMS logs each retention and recall decision as a memory event with an action, a reason, a policy id and a decision source (`wrapper.py`, `retain` and `recall`; Sec. 4.5). Engram's difference is that its log is the source of truth and replays state, not that it logs. |
| The first deterministic policy on memory reads | Already withdrawn in October (`docs/readings/litreview/README.md`, "Novelty claims"; 2606.24535, 2610.11188). HEAMS also offers deterministic rules (Sec. 4.2). |
| Their policies are free text read by a model | True of every policy HEAMS reports in its experiments (Sec. 4.2, Appendix D.2), not of its framework, which also has deterministic and hybrid modes. Not true of SAFE-Mem's gate, which is a comparison in code (Eq. 2), over labels a model partly assigns. |

## HEAMS

HEAMS (Goel et al., Mila and Mozilla) is a benchmarking framework that judges a memory system on performance, efficiency, privacy, user sovereignty and security side by side (Sec. 1). It puts six memory systems (no memory, in-context, Mem0, Letta, HippoRAG 2 and its own MilaMem) behind a common interface of retain, recall, delete and consolidate (Sec. 4.1, Sec. 5), and adds four benchmarks of its own: Contextual Integrity, Transparency, Editability and Erasability, and Retention Policy (Sec. 3.2).

Its governance layer wraps the memory interface with retention policies, applied before storage, and recall policies, applied to retrieved candidates before disclosure (Sec. 4.2, Figure 3). Each decision is binary, store or drop and expose or withhold. A policy is a deterministic content or metadata rule, a free-text policy interpreted by an LLM, or a hybrid (Sec. 4.2); in the code the deterministic rule is a substring and metadata match (`_rule_matches` in `retention_policy_deterministic.py`). Every experiment in the paper uses free-text policies judged by `openai:gpt-4o-mini` (Sec. 4.2, Appendix D.2). The governance layer is evaluated only with MilaMem (Table 3, caption), so the paper does not measure one policy across stores, although the framework is built to.

The governed numbers, all on MilaMem: recall governance cuts scenario leakage from 57.61 to 31.82 percent at a cost of 4.80 points of helpfulness, and gives the highest helpful and leak-free share, 45.95 percent (Table 5). Retention governance lowers the upper bound on prohibited recall from 100.00 to 15.63 percent while permitted recall falls from 100.00 to 84.47 percent (Table 7). Retention and recall governance together raise MPBench resistance from 40.00 to 88.61 percent over 360 attacks (Table 8). Each configuration has one reported run (Appendix C, reporting conventions), the agent runs at temperature 1 (Sec. 6), the LLM judges are not validated against human labels (Sec. 8), and the MPBench policies were developed on benchmark examples (Appendix C.6). The suite covers a single user's personal memory only (Sec. 2.2, Sec. 8).

## SAFE-Mem

SAFE-Mem (Li et al.) is a memory system, not a layer over other stores. It keeps a graph of sentence, claim and entity nodes (Sec. 4.2; `TypedStandingMemory` in `src/ams/memory/typed.py`), and every baseline it is compared with shares one memory of its own (Sec. 5.1).

Each claim carries a kind (DESCRIPTION, ATTRIBUTE, PREFERENCE, RULE, PERMISSION, ordered; `Rung` in `src/ams/core/lattice.py`), an authority (the strongest kind its source channel may establish) and a scope (whom that authority covers) (Sec. 4.1). Authority and scope come from channel records the runtime keeps (Sec. 3, Sec. 4.1). The kind is assigned by the model during claim extraction (Sec. 4.1, prompt Q.1), a model judgment over the principal's sentences decides when a request to remember raises authority (Sec. 4.1, prompt Q.3), and a model classifier reads the request alone and sets the kind of use it needs (Sec. 4.3, prompt Q.4; `self.use_type.required(query)` in `TypedStandingMemory.retrieve`). Admission is then a comparison in code: a claim enters only if the lower of its kind and authority reaches the required use, within scope, before ranking (Eq. 1 and 2; `_admits` in `typed.py`). Retrieval itself calls no model, and the defence adds 18 to 20 percent LLM calls over an undefended memory (Appendix O, Table 14).

The numbers: on MPBench, attack success falls from 26.7 to 2.6 percent on GPT-5.6-terra and from 49.8 to 6.2 percent on GPT-4o-mini, while recall rises from 75.9 to 86.3 and from 79.5 to 85.9 percent (Table 1, Sec. 5.2). Against SAFE-Mem's own graph with governance off, admission raises MPBench recall on GPT-4o-mini from 76.7 to 85.9 percent (Table 6), but lowers LoCoMo accuracy from 64.9 to 61.3 points on GPT-5.6-terra and from 58.4 to 54.6 on GPT-4o-mini (Appendix G). On EHRAgent under MINJA, no wrong-patient call executes, and 2.0 percent of the memories benign questions would retrieve are removed (Sec. 5.3).

## The differences

| | Engram | HEAMS | SAFE-Mem |
|---|---|---|---|
| What is governed | A plane over existing stores behind one adapter contract: files, Mem0, Letta (ADR 0013; `packages/adapters/src/`). | Any memory system behind its common interface (`PrivacyMemoryWrapper`, `wrapper.py`; Sec. 4.2), evaluated with MilaMem only (Table 3, caption). | Its own claim graph (Sec. 4.2; `TypedStandingMemory`); not a layer over other stores. |
| Policy form, and what evaluates it | Typed policy objects (read matrix, write rules, grants, retention) evaluated by one pure function in code (ADR 0006; `packages/core/src/policy/evaluate.ts`). | Deterministic substring and metadata rules, free text read by an LLM, or hybrid (Sec. 4.2; `retention_policy_deterministic.py`); all reported experiments use free text read by gpt-4o-mini (Appendix D.2). | A lattice comparison in code (Eq. 2; `_admits`) over labels of which the kind and the required use are set by a model (prompts Q.1 and Q.4), and authority and scope by channel records (Sec. 4.1). |
| Model calls on the decision path | None (AGENTS.md rule 4). | One judge call per entry or candidate in LLM mode (Appendix D.2); none in deterministic mode. | None at admission; a model call per extraction, per retention judgment and per distinct query's use (Appendix O). |
| Record of each decision | A `MemoryEvent` with actor, scope, decision, `reason` and `policy_id`, also mirrored into the pi session (`schema.ts`; AGENTS.md rule 3). | A memory event per retention and recall decision with action, reason, policy id and decision source (`wrapper.py`, `retain` and `recall`; Sec. 4.5). | Replay | Item state rebuilt from the log alone at any event (`replay.ts`; ADR 0003); a recorded workload replays every decision under any policy (ADR 0032). Not a single decision from events alone (ADR 0032, context). | Run records trace a score to its configuration, memory operations and model context (Sec. 4.4). No code path in the repository rebuilds memory state or re-decides from the log: a search for "replay" in `python_package/src` and `memory_plugins` finds only the Editability benchmark's replayed user turns and a results-browser comment about a benchmark run. | A cache of model responses lets a run be repeated (`src/ams/llm/pool.py`); no rebuild of state from a decision log was found. |
| Principals and scope | Scopes at four levels (person, role, team, org), membership, and read grants with class and expiry (ADR 0006, ADR 0021, ADR 0030). | One user's personal memory (Sec. 2.2, Sec. 8); the wrapper has no actor or scope. | A scope per claim, the principal or another party (Sec. 4.1); memory shared across users on EHRAgent (Sec. 5.3). |

| Delete and consolidate | Retirement and retention sweeps are governed and logged as events (ADR 0010, ADR 0025). | Passed through to the memory system ungoverned (`wrapper.py`, `delete` and `consolidate`); policies for them are future work (Sec. 4.2). | Nothing is deleted; a claim is withheld from a use, not from memory (Sec. 6.2; `README.md`). |

## What this means for the hypotheses

- **H1.** SAFE-Mem's Appendix M is the nearest published instance of H1's contrast: the same entries, enforced by withholding or left to the model with a label, and enforcement leaks less on both backbones. It is prior evidence for H1's direction on one benchmark, MPBench, and it makes the question less new. H1's registered design does not change.
- **H2.** SAFE-Mem reports higher recall than no defence, which seems to deny any governance tax. Its own ablation separates the two effects: the claim graph and its passages raise accuracy, and admission then costs 3.6 to 3.8 LoCoMo points against the same graph without it (Appendix G). H2's contrast, C2 against C5 on the same memory, is the governance-off comparison, not the no-defence one, so the two papers are consistent with a tax. HEAMS's helpfulness and permitted-recall costs (Tables 5 and 7) point the same way.
- **H4.** HEAMS's common interface is the nearest design to an across-store comparison, and it too reports governance on one system only. Engram states store independence as a property of its design, as ADR 0035 decided, and does not claim to have measured it.

## Corrections to the literature notes

The notes of PR #67 read the abstracts and parts of the papers. The full texts change four statements in `docs/readings/litreview/2611.20144-heams.md`, `2610.22959-safe-mem.md` and the November section of `sota-2026.md`. This card does not edit those files; the corrections are recorded here and in the log.

1. SAFE-Mem's recall without defence is 75.9 percent on GPT-5.6-terra and 79.5 percent on GPT-4o-mini (Table 1). The notes give 41.1, which is Qwen3.8-Flash's attack success without defence in the same row.
2. HEAMS's governance layer is evaluated only with MilaMem (Table 3, caption). The notes list Mem0, Letta, HippoRAG 2 and in-context as systems it wraps in the experiments.
3. HEAMS supports deterministic and hybrid policies (Sec. 4.2) and logs each decision with a reason and a policy id (`wrapper.py`). The notes say its policies are free text read by an LLM and contrast Engram's logged decisions with it.
4. HEAMS's retention-policy and MPBench numbers, unread in the note, are 15.63 and 84.47 percent (Table 7) and 40.00 to 88.61 percent (Table 8). Both repositories are Apache-2.0 at the commits above; the notes left the licences unchecked.
