## Claim
Reusable workflows should be governed by execution evidence: formalize a step into code only when enough traces support it, run code only when observable gates pass, fall back to natural language otherwise, and demote or retire on repair burden. This buys retention, fewer post-repair regressions and survival across software versions, which one-shot success does not measure.

## Method
A workflow is a versioned notebook of steps; each step has an intent, a natural-language procedure, an optional validated executable realization, and pre and post gates that are predicates over environment-observable state, never benchmark evaluators (Sec. 3.1). Lifecycle per version: provisional (under validation), released (retrievable), retired (kept for rollback and analysis) (Sec. 3.2). Creation needs tau_create similar traces; a step is formalized at tau_form supporting traces; a step is demoted to NL guidance at tau_demote accepted repairs; a workflow is retired when a token-weighted repair burden in [0,1], per-step burden capped at 1, crosses its threshold, deferred when the calibration set is empty (Sec. 3.2). Thresholds are chosen per group (site family, task type, action type, interface properties) as the cheapest threshold whose one-sided Wilson upper bound on the replay violation rate is at or below V_max, small groups shrunk toward the pool by n / (n + n_0) (Sec. 3.3). At runtime each step tries code, then NL procedure, then bare intent, stopping at the first that passes both gates; unresolved runs go to offline maintenance (Sec. 3.4). Base model gpt-5.3-codex for every method, 30-step cap (App. B). Baselines CodeAct, AWM online, ReasoningBank.

## Key numbers
- WebArena-Verified success: CodeAct 38.3, AWM online 46.4, ReasoningBank 49.8, SKILL.nb 53.7, CI 50.3 to 57.1; 3.9 points over ReasoningBank, McNemar p = 0.029 (Table 1, Sec. 1).
- Retention across three re-executions: 91.7 against 76.2 (ReasoningBank) and 71.6 (AWM online) (Figure 1b).
- Repair recovery / post-repair regression: 72.9 / 4.2 against 63.0 / 15.0 and 58.0 / 17.0 (Figure 1c, labelled budget 2).
- GitLab migration, 180 tasks, state frozen on 15.7, run on GitLab 18: AWM online fresh 88 (48.9 percent) to frozen 62 (34.4); ReasoningBank 90 to 70; SKILL.nb 110 (61.1) to 111 (61.7) (Sec. 4). Abstract: minus 1.7 points on 16.11, plus 0.6 on 18.9.
- Ablation, 258-task hard subset, SR / regression: full 38.4 / 3.3; NL-only 33.3 / 8.8; code-only 31.0 / 14.7; no gates 32.6 / 18.6; no demote 34.1 / 12.4 (Table 3).
- V_max 0.05, alpha 0.05, n_0 2, tau_recover 0.25, three repair attempts per failing artifact (App. B).

## What Engram borrows
The three states map onto candidate, active, retired (glossary, ADR 0011), with retired kept replayable, which is ADR 0010's retire-not-delete. Retention and post-repair regression join success as H5 metrics (D4). The Wilson upper bound gives the k of n admission rule a statistical form: pick k and n so the one-sided bound on failure is at or below a pre-registered V_max (S0.12). The GitLab migration is the template for the environment-change arm: an environment hash change triggers re-validation or retirement. Demotion instead of deletion is the model for narrowing on human rejection.

## What Engram does differently
SKILL.nb governs one workflow store inside one agent. Engram is a plane above any store, applies one lifecycle to every memory class, and logs each transition as an event with a reason. Engram v1 procedures are text, so there are no executable cells and no runtime gates; admission is replay on held-out tasks, and retirement follows the smoothed success rate and environment hash, not repair burden.

## Risk to our claims
Removing gates raises regression from 3.3 to 18.6 percent (Table 3): much of the durability is runtime gating, which Engram v1 lacks. A governed text procedure may retain no better than AWM, weakening H5. Mitigation: report retention explicitly, and treat gate predicates as a candidate lint on procedure preconditions in a later card.

## Open question
Thresholds are grouped by site family and interface properties. What is the grouping key for pi coding sessions: repository, tool set, task type? Pick one in step 0 before any replay numbers exist.
