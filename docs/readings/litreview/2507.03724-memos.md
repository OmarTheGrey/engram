## Claim
Memory should be a managed system resource with one unit, the MemCube, that carries content plus provenance, access control, lifespan and version lineage, across plaintext, activation (KV-cache) and parameter memory. A system built this way tops LoCoMo, LongMemEval, PreFEval and PersonaMem against commercial memory layers.

## Method
Three memory types with transformation paths between them (Sections 4.1, 4.2). A MemCube has descriptive metadata (timestamp, origin signature, semantic type), governance attributes (access control, lifespan policy, priority, compliance and traceability) and usage indicators (access patterns, contextual fingerprint, version chain) (4.2, Figure 6). Lifecycle states: generated, activated, merged, archived, expired (5.2). Three layers: interface (MemReader, Memory API with provenance, update and log-query calls), operation (MemOperator, MemScheduler, MemLifecycle with rollback), infrastructure (MemGovernance, MemVault, MemLoader, MemDumper, MemStore) (5.1 to 5.5). MemGovernance uses a ternary permission model over user, object and calling context, with TTL, redaction, watermarking and audit logs (5.5.1). Evaluation on four benchmarks with GPT-4o-mini for every method against MIRIX, Mem0, Zep, Memobase, Supermemory and MemU (6.1); KV-cache injection on three Qwen models (6.5).

## What Engram borrows
- MemCube is the closest published schema to Engram's item and ADR 0002 compares them field by field: origin signature maps to `provenance`, lifespan policy to `ttl` and `valid_to`, access control to `scope` and `grants`, version chain to `version` and `lineage`, lifecycle states to `status`.
- The ternary permission model (user, object, calling context) in 5.5.1 is a check on ADR 0006: Engram's read matrix is over scope and actor, and the calling context (which harness, which tool) is currently only in the event, not in the policy input.
- The Provenance API and LogQuery API (5.3.2) are the same surface as `memory_explain` and the inspector. Tables 3 to 6 are ready baseline numbers on GPT-4o-mini for the stores Engram wraps.

## What Engram does differently
MemOS is a store with governance inside it; Engram is governance outside any store, so the same policy applies to Mem0, Letta and files, which is what H4 tests. MemOS reports no measurement of its governance layer: no leak rate, no deletion compliance, no enforcement-versus-instruction comparison, and the paper has no limitations section. Engram's MemGovernance equivalent is the thing under test, not a feature list. Engram also never touches activation or parameter memory.

## Risk to our claims
If MemOS's governance attributes are enforced in its open-source release, then "a store with native governance" is a competitor condition H1 should include, and a plane above it adds only the cross-store part. We check the repository in step 0 (S0.6-style) for whether access control and audit logging are implemented or declared, and record the answer in PINS.md.

## Open question
MemOS's Section 7 proposes paid memory modules and a memory marketplace with contract-bound access. What would Engram's grant model need to express a memory an organisation licensed rather than owns, and is that in scope for the twin?
