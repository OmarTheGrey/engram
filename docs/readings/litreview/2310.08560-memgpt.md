## Claim
An LLM can manage its own memory hierarchy if it is given a fixed main context, two external tiers, and function calls to move data between them, the way an OS pages between fast and slow memory. The model, not the harness, decides what to keep.

## Method
Main context has three parts: read-only system instructions, a fixed-size working context editable only through function calls, and a FIFO message queue whose head is a recursive summary (Section 2.1). External context is recall storage (every message, searchable) and archival storage (arbitrary text, PostgreSQL with pgvector, Section 3.2.1). A queue manager warns the model at a token threshold (for example 70 percent) and flushes at another (for example 100 percent), summarising evicted messages (Section 2.2). Functions can set `request_heartbeat=true` to chain calls (Section 2.4). Evaluated on Multi-Session Chat for deep memory retrieval and conversation openers, and on multi-document QA and nested key-value retrieval, with GPT-3.5 Turbo, GPT-4 and GPT-4 Turbo against fixed-context baselines (Section 3).

## Key numbers
- Deep memory retrieval accuracy, Table 2: GPT-4 32.1 percent baseline to 92.5 percent with MemGPT; GPT-4 Turbo 35.3 to 93.4; GPT-3.5 Turbo 38.7 to 66.9.
- ROUGE-L recall, Table 2: GPT-4 0.296 to 0.814.
- Conversation opener, Table 3: GPT-4 with MemGPT SIM-1 0.868 versus human 0.800.
- Nested key-value, Section 3.2.2: GPT-3.5 baseline reaches 0 percent at one nesting level; GPT-4 and GPT-4 Turbo reach 0 percent by three levels; MemGPT with GPT-4 is unaffected by depth.
- Multi-document QA, Figure 5: reported as curves only, no values in text.

## What Engram borrows
- The function-call surface (`memory_write`, search, paginated read) is the shape of Engram's four governed tools (ADR 0001, item 2). Letta, MemGPT's successor, is one of the three stores the adapter must cover (ADR 0013), with memory blocks mapping to working context and archival to the searchable tier.
- Recall storage as a never-deleted log is the append-only event log idea (ADR 0003), though MemGPT logs messages, not decisions.
- The memory pressure warning is a precedent for policy-injected `custom_message` entries: the harness tells the model about memory state at a chosen moment.

## What Engram does differently
MemGPT puts memory management inside the model's action loop and trusts it. Engram puts a deterministic gate between the model's write call and the store, keeps the explanation of every recall outside the model, and never calls a model itself. MemGPT has no scope, owner, provenance or validity on a memory, so a fact written by the model and a fact stated by the user are indistinguishable; ADR 0004 makes `kind: model` untrusted by default.

## Risk to our claims
The gains depend entirely on the model's function-calling skill: GPT-3.5 collapses on document QA and nested retrieval (Section 3.2). H4 claims model-agnosticism for the plane, but if a weak model cannot issue well-formed governed tool calls, the governed condition will look worse than instruction-only for that model. We state H4 as "the plane's decisions are identical across models," not "the agent's score is," and report tool-call failure rate per model.

## Open question
MemGPT's working context is overwritten in place by the model. Should Engram's Letta adapter version every block edit as a superseding write (ADR 0005), even though Letta itself does not, and what does that cost in events per session?
