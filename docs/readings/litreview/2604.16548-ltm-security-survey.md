## Claim
Writable memory that persists across sessions creates threats that are persistent, stateful and propagating, and no defence bolted on at retrieval or execution time can cover them. The survey organises attacks and defences on a six-phase lifecycle (write, store, retrieve, execute, share and propagate, forget and rollback) against four objectives (integrity, confidentiality, availability, governance), finds store-time and forget-time defences nearly empty, and proposes Verifiable Memory Governance: five primitives a memory system needs for its state to be auditable and recoverable.

## Method
A taxonomy survey. Table 1 compares nine prior surveys to this one on lifecycle coverage, benign risk and conceptual framework. Table 2 orders five write-path attacks by attacker privilege (AgentPoison, InjecMEM, MINJA, MemoryGraft, eTAMP). Each phase gets an attack list and a defence list: write (VerificAgent, MemCube-style metadata), store (versioned snapshots, write logs, content-addressable records, W3C PROV, all described as underdeveloped), retrieve (RobustRAG, TrustRAG, SeCon-RAG, RevPRAG, A-MemGuard), execute (CaMeL, FIDES, PCAS, Progent, IsolateGPT), share (Collaborative Memory's principal-resource graph, BlindGuard), forget (RAGForensics, an OWASP agent-memory project) (Sec. 3, Sec. 4). VMG (Sec. 5, App. A Table 3): Write Authorization (every entry has an authenticated source and passes an explicit check before consolidation), Provenance Visibility (queryable lineage back to the originating write, preserved through summarisation and merging), Principal-Scoped Retrieval (only entries whose scope includes the requester), Rollbackability (snapshots and logs restore an exact prior state), Verified Forgetting (post-deletion probing recovers nothing above a bound epsilon). The system property is the conjunction (Eq. 6) and a design pre-order VF before RB before PV before WA says provenance must be built first (Eq. 7).

## Key numbers
- Write-path attack figures quoted from the primary papers: AgentPoison under 0.1 percent poison rate with over 80 percent attack success; InjecMEM 76.6 percent ASR on MemoryOS (Sec. 3.1, Table 2).
- Six phases, four objectives, five primitives, nine prior surveys compared (Table 1, Sec. 5).
- The number of papers surveyed is not stated in the sources read.

## What Engram borrows
VMG is a checklist Engram can claim to satisfy and should cite as such in the thesis. Write Authorization is ADR 0007 plus ADR 0004's source trust; Provenance Visibility is ADR 0004 with the requirement, which Engram has not yet written down, that provenance survives summarisation: a `compaction` item must carry `derived_from` ids so lineage is complete through merges. Principal-Scoped Retrieval is invariant 1 (ADR 0006). Rollbackability is ADR 0003's replay-from-events. Verified Forgetting is the gap: ADR 0010 retires rather than deletes, and ADR 0021 defers offboarding, so Engram should state honestly that it satisfies WA, PV, PS and RB and treats VF as a measured property via Bemula-style probing, not a guarantee. The survey's phase names also give ADR 0015 a coverage table: which benchmark exercises which phase.

## What Engram does differently
The survey asks for security guarantees inside the memory system; Engram's thesis is that the guarantees can be supplied above several stores that do not have them, which is the H4 claim. The survey's governance objective is a category; Engram's is a measured tax (H2). Where the survey lists Collaborative Memory's principal-resource graph as the share-time defence, Engram uses typed scopes and grants, which are simpler and simulable.

## Risk to our claims
The pre-order VF before RB before PV before WA says a system without verified forgetting cannot claim the rest under lineage-based deletion. If a reviewer applies VMG as a rubric, Engram's retire-not-delete stance reads as failing VF, and "retired items stay replayable" (ADR 0010) is the opposite of post-deletion unrecoverability. The thesis must separate the audit log (which must keep the retire event) from the item content (which can be hard-deleted for person-scope erasure, as ADR 0010 already allows) and show a probing test.

## Open question
The survey calls store-time defences underdeveloped and names W3C PROV as a candidate substrate. Should ADR 0004's provenance object be expressible as PROV-O so the explanation and lineage are exportable, or is that a v2 concern?
