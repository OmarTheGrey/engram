## Claim
An authorization engine can be built in the open as a readable executable model in Lean with proofs of its security properties, while the production Rust is kept honest by differential random testing against that model and by property-based tests where no model exists.

## Method
The team wrote an executable Lean model of Cedar's evaluator, authorizer and validator and proved properties on it, the largest being validator soundness (an accepted policy never raises a type error on evaluation). Production Rust is fuzzed against the Lean model (differential random testing, DRT) and property-based tests cover code with no model or proof. A release is blocked unless model, proofs and DRT are current.

## Key numbers
- 4 bugs found in the validator while proving, and 21 more by DRT and property tests (search summary of the paper; not re-read in full).
- Lean evaluates a DRT input in about 5 microseconds on average against 7 for Rust (same source).

## What Engram borrows
The shape, not the tooling: a small pure reference model of the write gate and read filter (the oracle in `packages/core/src/oracle.ts`, re-exported by `packages/core/test/property/oracle.ts`, already plays this role), differential testing of `Plane` against it, and a "model, proof and tests current" release gate. The pattern is largely realised already by the oracle and the seven invariants; a second reference gate (AB-FRM-6) was dropped as a duplicate. Per-step checking lands in AB-FRM-3. Lean itself is out of reach for the plane's TypeScript, so the model stays in Quint or TypeScript.

## What Engram does differently
Cedar's guarantees are about a policy language; Engram's are about a stateful protocol (event log, store, offboarding) where races matter more than evaluation, so a protocol model checker fits better than a theorem prover.

## Risk to our claims
A model and an implementation can agree and both be wrong against the intent; Cedar mitigates this by proving properties on the model. Our oracle has no proofs, only a second implementation.

## Open question
Which of the seven invariants are small enough to prove in Lean over the pure `evaluate.ts` decision function, as a thesis appendix?
