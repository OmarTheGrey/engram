## Claim
Memory should be organised the way a Zettelkasten is: each new note gets LLM-written keywords, tags and a context line, is linked to similar notes by an LLM, and may cause those neighbours to be rewritten. Linking gives most of the gain; evolution adds a little more.

## Method
A note is content, timestamp, keywords, tags, context, an embedding over all of them (all-MiniLM-L6-v2) and a link set (Section 3.1, Eq. 1). Link generation takes the top-k cosine neighbours and asks an LLM which to link (3.2). Memory evolution asks an LLM, per linked neighbour, whether to rewrite its context, keywords and tags; the rewritten note replaces the original (3.3). Retrieval is cosine top-k, default k = 10, with linked notes pulled in (3.4). Evaluated on LoCoMo (7,512 QA pairs, five categories) and DialSim (1,300 sessions, about 350k tokens) against LoCoMo full-context, ReadAgent, MemoryBank and MemGPT, on GPT-4o-mini, GPT-4o, Qwen2.5 1.5B and 3B, Llama 3.2 1B and 3B; F1 and BLEU-1 primary (Section 4).

- Table 1 tokens per question: A-Mem 2,520 (GPT-4o-mini) and 1,216 (GPT-4o) versus about 16,900 for baselines.
- Table 3 ablation, GPT-4o-mini F1 on temporal: no linking and no evolution 24.55; no evolution 31.24; full 45.85.
- Section 4.3: 5.4 s per operation with GPT-4o-mini, 1.1 s with local Llama 3.2 1B; cost estimated below 0.0003 dollars per operation.
- Table 4: memory grows linearly from 1.46 MB at 1k notes to 1,464.84 MB at 1M; retrieval 0.31 to 3.70 microseconds.
- Table 2 DialSim F1: A-Mem 3.45, LoCoMo 2.55, MemGPT 1.18.

## What Engram borrows
- A-Mem is the clearest published case of a store rewriting stored items without lineage (3.3: the evolved note "replaces the original"). ADR 0005 cites it as the reason an update must create a new version with `lineage` and set `valid_to` on the old one.
- The link set is a precedent for `lineage` as a graph rather than a chain; the orphan lint (an item whose links all point to retired items) comes from here.
- Table 4's scaling measurement is the template for the plane's overhead measurement in H2: items, bytes and read latency at 1k to 1M.
- The six-model evaluation is the model for H4's cross-model arm.

## What Engram does differently
A-Mem's three LLM calls per write (describe, link, evolve) all happen inside the store and leave no record of what changed or why. Engram makes each a `kind: model` provenance write that must pass the gate, logs the rewrite as a supersession, and can retire an evolved note whose source note is later retired. A-Mem has no scope, owner or validity.

## Risk to our claims
Evolution is worth about 15 F1 points on temporal (Table 3, 31.24 to 45.85) and it is exactly the behaviour ADR 0004 marks untrusted and ADR 0005 versions. If the governance tax (H2) comes from throttling or versioning store-internal rewrites, A-Mem is where it will show first. We measure H2 on the A-Mem-style path separately, and treat evolution rewrites as a per-scope budget rather than a block.

## Open question
When a neighbour's context is rewritten, is the neighbour's provenance still its original source, or does it now also depend on the new note? If the latter, the source-changed lint must follow links, which is a graph walk per write.
