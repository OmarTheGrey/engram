## Claim
A web agent can propose its own practice tasks, turn successful attempts into Python functions, test and debug those functions, and then use the resulting library to solve more tasks; libraries built by a stronger agent also help a weaker one.

## Method
Three stages (Sec. 3). Skill proposal: an LLM sees screenshots, URLs and accessibility trees and proposes short procedural, navigational or information-seeking tasks. Skill synthesis: the base agent practises the task, an LLM reward model judges success from the task, trajectory and environment feedback, and successful trajectories are turned into a Python function over Playwright whose docstring carries a usage log and the page state required before the call. Skill honing: each function is unit-tested; functions with no parameters beyond page run directly, otherwise the LLM generates test inputs; failures are debugged, and static analysis catches common generation mistakes with regeneration on hit. GPT-4o at temperature 0.3 is the default agent, GPT-4o-mini the weaker one; 10 steps per iteration and 160 exploration iterations per site (Sec. 4). Benchmarks: WebArena, 812 tasks on five sites, and a 57-task Online-Mind2Web subset on four live sites.

## Key numbers
- WebArena average success: GPT-4o 22.6 to 29.8 with skills; GPT-4o-mini 9.2 to 14.1; per site for GPT-4o, GitLab 17.8 to 22.2, Map 27.5 to 33.9, Shopping 19.8 to 27.2, CMS 18.7 to 25.8, Reddit 37.7 to 50.0 (Table 1).
- Online-Mind2Web success: average 40.2 to 56.2; Drugs 65.0 to 87.0, Flights 11.7 to 29.4, Cooking 62.5 to 75.0, Cars 11.1 to 11.1 (Table 2).
- Abstract states 31.8 percent and 39.8 percent relative gains, and up to 54.3 percent for the weaker agent; the tables give about 32, 40 and 45 percent on average, with per-site weak-agent gains of 40 to 133 percent in the text.
- Against human-written APIs, synthesized skills are comparable on sites with low or medium API support (Reddit, Shopping) and worse on high-support sites (GitLab, Map) (Figure 3).
- Honing's "verified" criterion is that the function runs without an exception, which a function that silences errors can satisfy (App. D.2.1).

## What Engram borrows
The required page state in the docstring is the precondition field on a procedure item; the usage log is the ancestor of the smoothed success rate (ADR 0011, D4). Testing with generated inputs shows replay needs inputs the induction did not see, which is why D3 validates on held-out tasks rather than the inducing session. Strong-to-weak transfer motivates a secondary analysis in ADR 0016: procedures induced under one provider's model replayed under the other two.

## What Engram does differently
Engram does not synthesize code in v1 and does not run an exploration curriculum; procedures come from real pi sessions. Validation is an outcome judgement on held-out tasks, not "no exception". SkillWeaver's library only grows; Engram retires procedures on drift or environment change and logs every transition.

## Risk to our claims
App. D.2.1 is the warning: a verification that checks completion rather than outcome admits procedures that do nothing. A replay judge that only checks that the procedure ran would reproduce the same hole, and H5 would count silent no-ops as passes. Mitigation: the replay judge is the vendored benchmark judge from ADR 0015, checking task outcome, and a lint flags procedures whose replay produces no store or filesystem change.

## Open question
Figure 3 shows less headroom where the site already exposes good APIs. Coding sessions sit on rich CLIs and tools. How much headroom do procedures have there at all, and does it depend on the repository? The step-0 session fixture should include at least one tool-rich and one tool-poor repository.
