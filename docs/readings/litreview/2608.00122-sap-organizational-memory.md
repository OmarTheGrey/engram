## Claim
An enterprise can capture what coding agents learn inside the coding workflow itself, with contributor approval at the point of capture, curate it into question-and-answer memories, screen it for secrets and PII, and serve it back over MCP; in a production deployment on selected SAP teams, 900 contributed learnings produced 1,144 curated memories, about half of learnings yielding at least one. The paper reports throughput and design, not utility.

## Method
Capture is wired into the coding assistant's hooks: a PostToolUse hook marks memory dirty only when a designated knowledge-base file changes, and a Stop hook diffs the local knowledge base against a replica with Diff Match Patch and sends nothing until the contributor approves (Sec. 2.1; the paper says the hooks follow the Claude Code mechanism). Curation runs an Enrichment Agent that turns hunks into zero or more QA memories, a Bucketing Agent for tags, a Collision Checker for dedup and linking, then trust-score initialization and persistence; LLM calls use Claude Sonnet 4.5 at temperature 0 (Sec. 2.2, App. C). A screening gate runs after enrichment and before trust scoring over six categories (dependency, secret, code, PII/internal, workflow, grounding) and maps to one of four actions: reject, persist rewritten, block, persist unchanged; there is no quarantine state (Table 3, Table 4, App. D). Retrieval is over Weaviate with gemini-embedding at 1536 dimensions and a Cohere reranker, exposed to agents through MCP and to humans through a UI, in Fast, Normal and Deep Research tiers (Sec. 2.3, App. E). Each memory carries a source id, contributor pseudonym and pseudonymous team; provenance, lines of business, feedback counters and timestamps are governance-only and not searchable (App. B).

## Key numbers
- Snapshot dated 22 July 2026: 900 contributed learnings; 483 (53.7 percent) yielded at least one persisted memory; 417 (46.3 percent) yielded none; 1,144 curated memories, 2.37 per productive learning; 1,100 (96.2 percent) have at least one semantic link; 7,863 links across 35 tools and frameworks (Sec. 4).
- Gate sanity check, offline and synthetic: 56 cases run three times, 168 executions; appropriate 135 (80.4 percent), cautious non-blocking 32 (19.0 percent), overcautious blocking 1 (0.6 percent), unsafe acceptances 0 (App. D.1, Table 7).
- Not reported: contributor count, approval rate, production screening rejections, retrieval hit rates, downstream task effect (Sec. 4, 5).
- Declared minimum similarity threshold 0.3 is not enforced; the `total_changes` intake invariant is not enforced in production (App. A, App. E).

## What Engram borrows
This is the closest industry description of a write gate with provenance on a coding-agent memory, and it confirms three Engram choices. The gate's four outcomes (reject, persist rewritten, block, persist unchanged) are a richer decision set than ADR 0007's admit or reject; "persist rewritten" is worth adding as a gate decision with the rewrite recorded as a new version with lineage (ADR 0005). Governance-only fields that are stored but not searchable (App. B) is the pattern for ADR 0002's `provenance` and `grants`: present on the item, excluded from the retrieval text. Contributor approval at capture is a user-kind provenance event (ADR 0004) and the pseudonymous contributor id is the `owner` field. Their explicit list of unimplemented hardening (encryption, tenant isolation, least privilege, auditable access control, retention and deletion, Sec. 7) is the list of things Engram's plane claims to add above a store, which makes this a useful "what a store team ships first" baseline for the thesis's related-work section.

## What Engram does differently
SAP's system is a store with curation; policy on who may read what is "authenticated internal access", a single scope. Engram has four scopes and grants, a read filter and explanations, and an event log that would answer the stage-level disposition question they say their telemetry cannot (Sec. 4), because every drop is an event with a reason (ADR 0003). Engram also measures utility against memory-off, which they list as future work.

## Risk to our claims
Their gate produced zero unsafe acceptances but also one overcautious block in 168 synthetic executions, and 46.3 percent of real learnings produced no memory at all (Sec. 4). If half of what agents learn never passes a gate, the governance tax (H2) shows up as missing memory rather than slower reads, and Engram's write-gate rejection rate on real pi sessions must be reported as a first-class number with reasons, not only the downstream accuracy.

## Open question
Curation happens after the task, without the task context, and the authors note an incorrect but unsuspicious memory can be served before feedback lowers its trust (Sec. 6). Does Engram's `session_entry_id` on provenance plus replay from the event log let a lint re-examine a memory against its originating session, and is that cheaper than their feedback loop?
